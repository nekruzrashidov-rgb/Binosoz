## Preview 🌐

**https://binosoz-preview.vercel.app** — превью мультистраничного фронтенда (29.10.2026, проект Vercel `binosoz-preview`).

- Страницы отдаёт Vercel; `frontend/vercel.json` переводит `/login`, `/cabinet`, `/crm`, `/platform` на свои `.html`.
- Данные — настоящие, с локального API: Vercel проксирует `/api` и `/hubs` во временный туннель Cloudflare (`trycloudflare.com`) к API на компьютере разработчика. Адрес туннеля меняется при каждом запуске, поэтому в репозиторий он не попадает: прокси прописан только в копии фронтенда для деплоя.
- API для превью работает в режиме **Staging**: кода `123456` нет, коды входа приходят на настоящую почту через SMTP. Лимиты запросов подняты, потому что все посетители приходят к API с адреса прокси Vercel.
- Проверено: главная с данными API, `/crm` без входа → `/login`.
- **Ограничения:** превью работает, только пока на компьютере запущены API (Staging, порт 5195) и `cloudflared`. После перезапуска туннеля превью надо передеплоить с новым адресом. Чат идёт без WebSocket (Vercel их не проксирует) — SignalR переключается на запасной транспорт. Нет курса USD — `/rates/current` отвечает 404.
- **Постоянное решение:** API на VPS по `docs/DEPLOY.md` и адрес API в прокси Vercel вместо туннеля.

### Общий кэш: Redis вместо памяти процесса (30.10.2026)

Всё, что API держал в памяти процесса, теперь лежит в `IDistributedCache`: с Redis — общий для всех экземпляров API и переживает их перезапуск; без Redis — тот же интерфейс в памяти (`MemoryDistributedCache`), как раньше.

**Сделано ✅**
- [x] Пакет `Microsoft.Extensions.Caching.StackExchangeRedis` 10.0.14 (`StackExchange.Redis` приходит с ним). `RedisOptions` (`Redis:ConnectionString`, `Redis:InstanceName` = `binosoz:`). Кэш выбирается при создании, как и строка подключения к базе: строка задана — `RedisCache`, пустая — кэш в памяти. `AddMemoryCache()` убран: других пользователей `IMemoryCache` не осталось.
- [x] **`CatalogCache`** на `IDistributedCache`, 30 секунд, JSON. Сбросить всё разом в `IDistributedCache` нельзя, поэтому ключи живут в «поколении»: `catalog:{поколение}:{ключ}`, `InvalidateAsync()` записывает новое поколение в `catalog:gen`. Поколение — случайное значение, а не счётчик +1: у `IDistributedCache` нет атомарного увеличения, и два одновременных «прочитал 5 — записал 6» на разных экземплярах потеряли бы один сброс. Как и раньше, прочитанное во время изменения каталога в кэш не кладётся. Если Redis недоступен, каталог читается из базы, в лог — предупреждение. Все места сброса (брони, сделки, каталог, бренд) уже асинхронные и вызывают `await InvalidateAsync(ct)` — синхронная обёртка с `GetAwaiter().GetResult()` не понадобилась.
- [x] **`AuthService`.** В задаче — «чёрный список отозванных refresh-токенов в кэше», но такого кэша не было: отзыв refresh-токенов всегда хранится в базе (`RefreshTokens.RevokedAt`, повторное использование гасит все сессии), а это уже общее и надёжное хранилище. В `IMemoryCache` лежали две другие вещи, и именно они ломались бы при нескольких экземплярах API — их и перенёс:
  - запрос второго фактора создателя платформы (`2fa:{хеш}`, 5 минут, число попыток хранится вместе с ним и живёт до того же срока): код, принятый одним экземпляром, теперь можно подтвердить на другом;
  - счётчик неудачных входов по паролю на несуществующую почту (`login-failures:{почта}`, окно и порог как у Identity), чтобы блокировка действовала на всех экземплярах.
- [x] **«В сети» (`PresenceTracker`)**: `presence:{userId}` со временем в ISO на 6 минут (5 минут окна + минута запаса). Интерфейс стал асинхронным (`TouchAsync`, `LastSeenAsync`). Экземпляр API обновляет отметку не чаще раза в минуту, а не на каждый запрос. Сбой кэша не ломает запрос: сотрудник просто «не в сети».
- [x] **docker-compose**: сервис `redis` (`redis:7-alpine`, проверка `redis-cli ping`), API получает `Redis__ConnectionString: redis:6379,abortConnect=false` и ждёт Redis. В продакшене Redis наружу не открыт, данные на диске (`appendonly`, том `redisdata`), предел 256 МБ с вытеснением записей со сроком.
- [x] Тесты (`Catalog/CatalogCacheTests.cs`): второй вызов — из кэша, после сброса — снова из базы; изменение во время чтения не кэшируется; при «упавшем» кэше значение берётся из базы; без Redis API получает `MemoryDistributedCache`. Второй фактор и блокировки входа проверяют прежние тесты — уже на новом кэше. `dotnet build --warnaserror` без предупреждений, `dotnet test` — 216 из 216.
- [x] Development без Redis: API стартует, каталог `/api/v1/buildings` — первый запрос ~470 мс, следующие ~25 мс (из кэша), сайт и CRM работают.

**Продакшен**
- Нужна переменная `Redis__ConnectionString`. В `docker-compose.prod.yml` она уже задана (`redis:6379,abortConnect=false`) — отдельный Redis ставить не нужно.
- Railway / Render: добавить Redis (аддон) и задать `Redis__ConnectionString` строкой из аддона в формате StackExchange.Redis, например `host:port,password=…,ssl=true,abortConnect=false`. Адрес вида `redis://…` нужно переписать в этот формат.

## 1. Кратко

**Что это.** Backend платформы застройщика: один REST API для трёх клиентов — сайта с 3D-домом, CRM менеджеров и личного кабинета покупателя. Бронь с сайта сразу видна в CRM, платежи и документы из CRM сразу видны покупателю.

**Стек:**
- .NET 10 (SDK 10.0.303), ASP.NET Core Web API с контроллерами;
- PostgreSQL 18, EF Core 10 (Npgsql), 7 миграций;
- ASP.NET Core Identity + JWT;
- FluentValidation, Serilog, Swagger (Swashbuckle), Hangfire (хранилище в PostgreSQL), SignalR, QuestPDF, ClosedXML.

**Архитектура:**
- **`Sitora.Domain`** — сущности, перечисления, DTO, интерфейсы сервисов и внешних интеграций, исключения. Других проектов не знает; подключён только пакет `Microsoft.Extensions.Identity.Stores` (ради `AppUser`).
- **`Sitora.Infrastructure`** — `AppDbContext`, конфигурации таблиц, миграции, сидер, вся бизнес-логика в `Services/`, интеграции (заглушки SMS, Telegram, НБТ; локальное хранилище файлов; QuestPDF), фоновые задачи, JWT и шифрование.
- **`Sitora.WebApi`** — тонкие контроллеры, хаб SignalR, middleware (ошибки → Problem Details, защитные заголовки), валидаторы, `Program.cs`, Dockerfile.
- **`tests/Sitora.Tests`** — модульные и интеграционные тесты.

**Тесты.** 31 файл, 135 тестовых методов; при запуске — 152 случая, все проходят. Интеграционные тесты поднимают настоящий API (`WebApplicationFactory`) на временной базе PostgreSQL 18. Покрыто:
- вход, refresh, блокировка, SMS-вход, пользователи;
- каталог, импорт из Excel, миграции на существующих данных;
- брони, включая 10 одновременных запросов на одну квартиру;
- сделки и этапы, клиенты, заявки, CRM;
- расчёт графика, платежи, сторно, пересчёт по курсу, эквивалент TJS/USD;
- документы и подписанные ссылки, акт сверки и PDF графика;
- отчёты бухгалтера, стройка, чат (REST и SignalR);
- права по ролям и изоляция покупателя;
- лимиты, CORS, заголовки, Production и Staging, health-check, команды `--migrate` и `--healthcheck`.

## 2. Функции по ролям

Admin входит во все наборы ролей, кроме кабинета покупателя (`/me/deals`). «Сотрудник сделки» — это Manager, Accountant и Admin.

**Гость (без входа):**
- каталог: `GET /buildings`, `/buildings/{id}`, `/buildings/{id}/floors`, `/floors/{id}/apartments`, `/apartments/{id}`;
- заявка `POST /leads`, бронь `POST /apartments/{id}/bookings` (указывает имя и телефон);
- текущий курс `GET /rates/current`;
- скачивание по подписанной ссылке `GET /files?token=…`;
- вход: `POST /auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/sms/send`, `/auth/sms/verify`.

**Customer (покупатель):**
- свои сделки `GET /me/deals`;
- по своей сделке: график `GET /deals/{id}/schedule`, PDF графика `/schedule.pdf`, акт сверки `/statement.pdf`, документы `/documents` и ссылка на документ `GET /documents/{id}/download`;
- чат: `GET`/`POST /deals/{id}/messages` и SignalR `/hubs/chat`;
- ход стройки `GET /buildings/{id}/stages` — только по домам, где у него есть неотменённая сделка;
- чужая сделка везде отвечает 404, адреса сотрудников — 403.

**Manager (продажи):**
- заявки `GET /leads`, `PATCH /leads/{id}`;
- брони: создание на клиента, продление `POST /bookings/{id}/extend`, отмена `/cancel`;
- клиенты `GET`/`POST /customers`, `GET /customers/{id}`;
- сделки `GET`/`POST /deals`, `GET /deals/{id}`, `PATCH /deals/{id}/stage`;
- CRM `GET /crm/summary`, `/crm/pipeline`;
- график `POST /deals/{id}/plan`;
- загрузка документов `POST /deals/{id}/documents`;
- просмотр графика, PDF, документов, чат по любой сделке, ход стройки.

**Accountant (бухгалтер):**
- платежи `POST /deals/{id}/payments` и сторно `POST /payments/{id}/reverse`;
- курс `PUT /rates`;
- отчёты `GET /reports/payments`, `/reports/payments.xlsx`, `/reports/debts`, `/reports/debts.xlsx`;
- загрузка документов, просмотр графика, PDF, документов и чат по любой сделке, ход стройки.

**Content (контент):**
- дома, этажи, квартиры: `POST`/`PUT /buildings`, `/floors`, `/apartments`;
- «под запрос» `PATCH /apartments/{id}/on-request`;
- импорт `POST /apartments/import`;
- этапы стройки: `POST /buildings/{id}/stages`, `PUT /stages/{id}`, фото `POST /stages/{id}/photos`, просмотр хода стройки.

**Admin:**
- всё, что выше (кроме `/me/deals`);
- аудит `GET /audit`;
- пользователи: `GET`/`POST /users`, блокировка и разблокировка `PATCH /users/{id}/status`.

## 3. Модули

### Вход и безопасность
- **Сотрудники** входят по почте и паролю. Пароль: не короче 8 символов, с цифрой, строчной и заглавной буквой.
- **Токены.** Access-токен JWT (HMAC-SHA256) живёт 15 минут. Refresh-токен — 30 дней; в базе хранится только его SHA-256, при каждом обновлении он меняется. Повторное использование старого refresh-токена отзывает все сессии пользователя.
- **Блокировка.** После 5 неверных паролей вход закрыт на 15 минут. Несуществующая и отключённая почта отвечают так же: тот же счётчик, та же блокировка, проверка пароля по фиктивному хешу. Поэтому по ответу и по задержке не понять, есть ли такая учётная запись. Разблокировка админом снимает и эту блокировку; блокировка админом отзывает refresh-токены.
- **Покупатели** входят по SMS-коду: 6 цифр, живёт 5 минут, 5 попыток, не больше 5 кодов в час на номер (дальше 429). Ответ `sms/send` одинаковый для любого номера, SMS уходит только существующим клиентам. При первом входе создаётся учётная запись с ролью Customer.
- **Лимиты по IP:** вход и refresh — 10 в минуту, `sms/send` и `sms/verify` — 20 в час, заявки и гостевые брони — 30 в час.
- **Общий лимит:** гостю 300 запросов в минуту на IP, вошедшему 600 в минуту на пользователя; `/health` не ограничен. Ответ 429 в формате Problem Details на русском.
- **Изоляция покупателя.** Каждый сервис сделки, документа, чата и стройки проверяет владельца через `DealAccess`. Чужая сделка неотличима от несуществующей: тот же 404 и тот же текст.
- **Прочее:**
  - паспортные данные шифруются AES-256-GCM и отдаются только в карточке клиента (Manager, Admin);
  - CORS — только домены из настроек;
  - заголовки `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, CSP; заголовка `Server` нет;
  - в Production — HSTS и редирект на HTTPS;
  - ошибки — Problem Details без стека.
- **Обязательные настройки.** При старте API проверяет строку подключения, `Jwt__Key` и `Encryption__Key` и, если чего-то нет, завершается с одной понятной строкой на русском (код 1) вместо стека исключения.
- **Статический анализ.** Включены все правила безопасности встроенных анализаторов .NET (`Directory.Build.props`); CI собирает с `--warnaserror`, поэтому новая находка ломает сборку.

### Каталог
- **Дома.** Название и описание на русском и таджикском (`NameRu`/`NameTg`, `DescriptionRu`/`DescriptionTg`). Язык выбирается по `Accept-Language` (`ru`, `tg`); если таджикского описания нет, отдаётся русское.
- **Этажи.** Этаж 0 — коммерческий. У каждого этажа есть счётчики всех и свободных квартир.
- **Квартиры:**
  - номер, комнат (0 — студия), площадь, цена за м²;
  - цена = площадь × цена за м² с округлением до 100 сомони;
  - статус Free, Booked, Sold или OnRequest;
  - `PlanSlot` — обязательная позиция 0–7 на плане этажа, уникальна в пределах этажа (проверяет база);
  - `Model3dId` — необязательный объект в 3D-модели.
- **Статус** меняют только методы сущности, которые вызывают бронь, сделка и «под запрос»; напрямую через PUT его не поменять.
- **Импорт из Excel** (столбцы A–G: этаж, номер, комнат, площадь, цена за м², позиция, ID 3D). При любой ошибке ничего не сохраняется, ответ 422 со списком ошибок по строкам. Пустой столбец G не стирает уже заданный `Model3dId`.
- **Кэш.** Публичный каталог кэшируется на 30 секунд; любое изменение каталога или статуса квартиры сбрасывает кэш сразу.

### Бронирование
- Бронь живёт 48 часов.
- На квартиру — одна активная бронь. Защита двойная: блокировка строки квартиры `FOR UPDATE` в транзакции и частичный уникальный индекс `Bookings(ApartmentId) WHERE Status = 'Active'`. Повторная бронь отвечает 409.
- Гостевая бронь создаёт заявку и уведомление менеджерам. Гость может держать одну активную бронь на номер телефона.
- Продление (+48 часов от более позднего из «срок брони» и «сейчас») и отмена с причиной — Manager и Admin.
- Задача Hangfire раз в 5 минут снимает просроченные брони, освобождает квартиры и пишет аудит.

### Сделки и этапы
- **Этапы:** Lead → Showing → Booking → Contract → Payment → Completed, плюс Cancelled. Вперёд — свободно; назад и отмена — только с причиной и записью в аудит. Completed и Cancelled — конечные.
- **Квартира и сделка.** С этапа Booking квартира Booked, с Contract — Sold. При возврате назад квартира снова становится Booked или Free. На квартиру допускается одна неотменённая сделка (частичный уникальный индекс).
- **Цена** копируется в сделку при создании и потом не меняется. Скидка — от 0 и меньше цены, при скидке больше нуля нужна причина.
- **Сделка в USD.** Цена = цена в сомони ÷ курс на сегодня, округление до 1 доллара. Без курса сделку не создать (422).
- **Бронь покупателя** (по клиенту или по телефону заявки) переходит в сделку. Бронь другого человека — 409.

### График платежей и платежи
- **График:** первоначальный взнос в процентах, срок 1–360 месяцев, день платежа 1–28. Месячный платёж = (цена − взнос) ÷ месяцы с округлением до целой единицы валюты; последний платёж забирает остаток округлений. Пересоставить график можно, пока нет платежей.
- **Распределение оплат.** Платёж закрывает самые ранние пункты: после каждого платежа и сторно все пункты пересчитываются от общей оплаченной суммы.
- **Пересчёт по курсу.** Если в договоре или платеже есть USD, берётся курс на дату оплаты или ближайший более ранний и сохраняется в `RateUsed`. У платежа хранятся суммы в валюте платежа, в валюте договора и в сомони. Нельзя:
  - платить без графика;
  - платить сверх остатка;
  - ставить будущую дату.
- **Сторно.** Платежи не удаляются. Сторно — обратная запись с тем же курсом и ссылкой на исходный платёж, датируется днём исправления. Платёж можно сторнировать один раз (уникальный индекс), сторно сторнировать нельзя.
- **Курс** вводят Accountant и Admin (`PUT /rates`), не дальше чем на завтра.
- **Эквивалент TJS/USD.** В графике есть сумма во второй валюте по текущему курсу с пометкой «оценочно»; без курса эквивалента нет.

### Документы и PDF
- **Документы:** PDF, PNG, JPG, DOCX до 20 МБ; тип проверяется по первым байтам файла. Загружают Manager, Accountant, Admin. Файлы лежат на диске (`Storage:RootPath`).
- **Подписанные ссылки на 15 минут.** `GET /documents/{id}/download` проверяет права и возвращает `{ url, expiresAt }`; по `url` файл скачивается без входа. Фото стройки тоже отдаются только такими ссылками. Подпись — HMAC-SHA256 над типом, Id и сроком. Подделанная, просроченная или чужого типа ссылка — 404.
- **Акт сверки** (`/statement.pdf?date=…`): начислено, оплачено, задолженность, остаток и список платежей с курсами на выбранную дату.
- **PDF графика** (`/schedule.pdf`): пункты со статусами, итоги и, если введён курс, столбец оценочного эквивалента.
- PDF строит QuestPDF со встроенным шрифтом Lato (кириллица и таджикские буквы проверены тестом).

### Отчёты бухгалтера
- **Поступления за период** (`/reports/payments`): по умолчанию текущий месяц, не больше 366 дней. Платежи и сторно (с минусом), итоги по валюте платежа и общий итог в сомони.
- **Задолженность на дату** (`/reports/debts`): по умолчанию сегодня. Сделки с просрочкой по графику: сумма, с какой даты, сколько дней, остаток по договору. Для прошлой даты распределение оплат пересчитывается по платежам до этой даты. Отменённые сделки не учитываются.
- Оба отчёта есть в JSON и `.xlsx`. Доступ — Accountant и Admin.

### CRM, чат, стройка, аудит
- **CRM.** `/crm/summary`: заявки, активные брони, истекающие за 24 часа, сделки по этапам, квартиры по статусам, сумма продаж. `/crm/pipeline`: колонки по этапам; в «Заявке» — открытые заявки без брони, в «Брони» — активные брони без сделки.
- **Клиенты.** Клиента можно завести из заявки: заявка закрывается, её брони переходят на клиента.
- **Чат.** Одна ветка на сделку. История — от новых к старым; сообщения другой стороны отмечаются прочитанными. Хаб `/hubs/chat`:
  - `JoinDeal` проверяет доступ;
  - `SendMessage` отправляет сообщение;
  - событие `messageReceived` приходит на каждое новое сообщение, в том числе отправленное через REST;
  - токен можно передать в `?access_token=`.

  Второй стороне уходит уведомление.
- **Стройка.** Этапы с процентом 0–100 и порядком; общая готовность — среднее по этапам. Фото PNG или JPG до 10 МБ.
- **Аудит.** Статусы, цены, платежи, сторно, документы, курс, этапы стройки, пользователи и заявки пишутся в `AuditLog`: кто, когда, значения «до» и «после». Запись сохраняется в той же транзакции, что и изменение. Просмотр — `GET /audit` (Admin) с фильтрами.

### Фоновые задачи Hangfire
- `expire-bookings` — каждые 5 минут снимает просроченные брони;
- `update-rates` — каждый день в 05:00 UTC (10:00 по Душанбе) загружает курс через `IRateProvider` (сейчас заглушка); введённый вручную курс не перезаписывает;
- `health-alert` — каждые 5 минут проверяет `ready` и сообщает о смене состояния.

Хранилище Hangfire — та же база PostgreSQL. Сервер задач выключается переменной `Hangfire__ServerEnabled=false`. Дашборд не подключён.

### Здоровье и логи
- `/health/live` — процесс отвечает, без проверок.
- `/health/ready` и `/health` — база, запись в хранилище файлов и (где запущен) сервер Hangfire. Ответ — JSON со статусами проверок, без текстов ошибок. При проблеме с базой или файлами — 503; остановленные фоновые задачи дают `Degraded` с кодом 200. `/health*` не перенаправляется на HTTPS.
- `dotnet Sitora.WebApi.dll --healthcheck` — проверка контейнера: запрос к `/health/live`, код выхода 0 или 1.
- Оповещение о сбое и восстановлении уходит через `INotificationSender` (сейчас заглушка Telegram).
- **Логи** — Serilog. В Production — JSON в stdout и в файлы `logs/sitora-ГГГГММДД.log` (по дням или по 100 МБ, хранятся 14 файлов). В записи о запросе есть `ClientIp` и `UserId`; запросы к `/health` в обычный лог не пишутся; строка запроса с токенами в лог не попадает.

## 5. Что проверено и как

- **Тесты.** 152 случая (`dotnet test`), все проходят. Сборка Release с `--warnaserror` — без ошибок и предупреждений. Каждый интеграционный тестовый класс поднимает API на своей временной базе PostgreSQL 18, которую тесты создают и удаляют; модульные тесты (расчёт графика, правила домена, PDF, оповещения) работают без базы. Отдельно проверены:
  - 10 одновременных броней одной квартиры — успешна ровно одна;
  - частичный уникальный индекс брони — в обход сервиса;
  - две вручную исправленные миграции — на уже существующих данных (описание остаётся русским, позиции назначаются по порядку номеров);
  - таджикские буквы в PDF;
  - обмен сообщениями через SignalR-клиента;
  - команды `--migrate` и `--healthcheck` — отдельными процессами.
- **Дамп и восстановление.** Без Docker, теми же командами и флагами, что в `scripts/backup.sh` и `scripts/restore.sh`, на локальном PostgreSQL 18:
  - база с данными сидера (128 квартир, 10 клиентов, 5 сделок, 25 пунктов графика, 3 платежа) после `pg_dump --format=custom --no-owner` и `pg_restore --clean --if-exists --no-owner` совпала построчно во всех 27 таблицах — и в пустой базе, и поверх изменённой;
  - команды `tar`/`find` для папки файлов восстанавливают удалённый файл и убирают лишний.
- **Production без Docker.** Сборка опубликована той же командой, что в Dockerfile, и запущена с `ASPNETCORE_ENVIRONMENT=Production` за имитацией прокси:
  - без миграций не стартует (код 1, подсказка с `--migrate`), `--migrate` готовит базу и создаёт первого админа;
  - `/health/ready` отвечает 200 (база, файлы, сервер Hangfire), `/health/live` по HTTP — 200;
  - остальное API по HTTP перенаправляется на HTTPS (307), HSTS есть;
  - Swagger закрыт (404), чужой Host получает 400;
  - вход bootstrap-админа работает, `--healthcheck` возвращает 0;
  - логи — JSON в файле, с IP клиента, без паролей.
- **Compose-файлы.** Оба проходят `docker compose config`: синтаксис и обязательные переменные.
- **Локальный запуск.** `dotnet run` из `backend/src/Sitora.WebApi` в обычном терминале без переменных окружения: секреты берутся из user secrets, окружение Development, `/health/ready` — 200, Swagger открывается, вход всех четырёх сотрудников сидера работает, каталог отдаёт дом из сидера.

## 6. Что не проверено или не готово

- **Docker не запускался.** На машине разработки нет WSL. Docker-образ ни разу не собирался, `docker compose up` (и сервис `migrate`) не запускался, Caddy и выпуск HTTPS-сертификата не проверены. Скрипты `backup.sh` и `restore.sh` целиком не выполнялись — проверены только их команды. Инструкция `docs/DEPLOY.md` на VPS не проходилась.
- **CI ни разу не запускался.** У репозитория нет удалённого репозитория на GitHub; синтаксис workflow проверен разбором YAML.
- **Testcontainers** в тестах не выполнялись: все прогоны шли через `SITORA_TEST_DB` на локальном PostgreSQL под Windows. Поведение под Linux (культура `tg`, PDF) не проверено.
- **Заглушки:** SMS (`SmsSender`), Telegram (`TelegramNotificationSender`), курс НБТ (`NbtRateProvider`). Они пишут в лог (Telegram — ещё и в таблицу `Notifications`). Вне Development вход покупателей по SMS не работает, курс USD вводится вручную.
- **Не сделаны пункты плана:**
  - 14 — тексты ошибок на таджикском (все ошибки только на русском);
  - 17 — настройки для Admin;
  - 22 — отвязать Domain от пакета Identity (принято как решение, не делается).
- **Хранится в памяти процесса** и сбрасывается при перезапуске:
  - кэш каталога (30 секунд);
  - счётчики лимитов запросов;
  - счётчик неудачных входов для несуществующих почт;
  - последнее состояние health-оповещения (после перезапуска сообщение может повториться);
  - подключения и группы SignalR.

  Для нескольких экземпляров API понадобятся Redis (кэш, лимиты) и backplane SignalR.
- **DAST** (сканирование запущенного API, например OWASP ZAP) не проводился.
- **Не измерялось:** скорость каталога (цель — 300 мс для 95% запросов) и работа под нагрузкой.
- **Не проверялось:**
  - SignalR через настоящий WebSocket и браузер (тесты — long polling);
  - импорт реального прайса застройщика;
  - формат данных НБТ;
  - лицензия QuestPDF (Community, до 1 млн долларов выручки);
  - требования закона РТ о персональных данных.
- **Полное падение API** изнутри не обнаружить: нужна внешняя проверка `/health/ready`.

## 7. Отклонения от ТЗ и принятые решения

Подробно — в `docs/DECISIONS.md`. Основные:
- PostgreSQL из dev-compose проброшен на порт **5433**, чтобы не мешать локальному серверу на 5432.
- **Роли** хранятся в таблицах Identity (`Roles`, `UserRoles`), а не полем `Role` в `Users`.
- Добавлен этап сделки **Cancelled**; Completed и Cancelled — конечные.
- **Цена квартиры** везде округляется до 100 сомони.
- **Этаж 0** — коммерческий, отдаётся вместе с жилыми (у дома из сидера 17 этажей, 16 жилых по 8 квартир). Номер квартиры — целое число (в сидере `этаж × 100 + позиция`), студия — `Rooms = 0`.
- **`PlanCoords`** из ТЗ сделан как `PlanSlot` (0–7) и `Model3dId`.
- Для «под запрос» добавлен `PATCH /apartments/{id}/on-request`, для этапов стройки — `POST /buildings/{id}/stages`.
- Добавлены исключения домена `UnauthorizedException` (401) и `TooManyRequestsException` (429).
- **Admin** входит во все наборы ролей; менеджеры видят все сделки и заявки, а не только свои.
- **Гость** держит одну активную бронь на номер телефона; бронировать на клиента может только Manager.
- **График и платежи:**
  - день платежа 1–28;
  - платёж без графика и сверх остатка не принимается;
  - сторно датируется днём исправления.
- **Сделка в USD:** цена пересчитывается по курсу на день создания и округляется до 1 доллара.
- **Миграции** в Production — только командой `--migrate` (сервис `migrate`); в Development и Staging — при старте.
- **Первый администратор** вне Development — из `BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD`.
- **Файлы** на диске, ссылки подписывает само приложение; ключ выводится из `Jwt__Key`.
- **Логи** — в файлы, а не в Seq; отказ фоновых задач в health-check — `Degraded`, а не 503.
- **Курс USD** в сидер не добавлен, чтобы не выдумывать банковские данные.
- **Язык:** `Accept-Language` влияет на название и описание дома, тексты ошибок только на русском.
- **Телефоны** принимаются только таджикские (`+992`).
- **Решение** — `Sitora.sln`, а не `.slnx`.

## 8. Изменения для фронтенда

Что изменилось в API с момента, когда его можно было подключать (этапы 1–6), по доработкам нового ТЗ:
- **Скачивание документа.** `GET /documents/{id}/download` возвращает `{ url, expiresAt }`, а не сам файл. Файл скачивается по `url` (относительный адрес; добавьте адрес API) без JWT в течение 15 минут.
- **Фото стройки.** `url` у фото в ответе этапа — подписанная ссылка на 15 минут, её можно ставить прямо в `<img src>`. Старый `GET /construction/photos/{id}` удалён.
- **Описание дома.** Поле `description` в запросах создания и изменения дома заменено на `descriptionRu` и `descriptionTg`. В ответе есть `description` (на языке запроса), `descriptionRu` и `descriptionTg`.
- **Квартира.** В запросах создания и изменения обязателен `planSlot` (0–7), можно передать `model3dId`. В ответе — оба поля.
- **Импорт Excel.** Столбец F (позиция на плане) обязателен, G (ID в 3D-модели) необязателен.
- **График.** В ответе появились `equivalent` (валюта, курс, дата курса, `isEstimate`, примечание, итоги) и у пунктов `amountDueEquivalent` и `amountPaidEquivalent`; без курса это `null`. Новый `GET /deals/{id}/schedule.pdf`.
- **Health-check.** `/health` возвращает JSON (`status`, `checks`), а не текст `Healthy`. Добавлены `/health/live` и `/health/ready`.
- **Лимит запросов.** Общий лимит: при превышении любой адрес может ответить 429 с заголовком `Retry-After`.
- **Несуществующая почта** после 5 неудачных входов отвечает «слишком много попыток», как настоящая.
- **Новые адреса:** отчёты `/reports/*`, `GET /files?token=…`, `PATCH /users/{id}/status`.

## 9. Как запустить

**Локально без Docker** (нужны .NET 10 SDK и PostgreSQL 18). Нужны настройки:
- `ConnectionStrings__Default`
- `Jwt__Key` (не короче 32 символов)
- `Encryption__Key` (32 байта в base64)
- `SEED_ADMIN_PASSWORD` и при желании `SEED_MANAGER_PASSWORD`, `SEED_ACCOUNTANT_PASSWORD`, `SEED_CONTENT_PASSWORD`

Их можно задать переменными окружения или, для разработки, через user secrets (хранятся в профиле Windows, вне репозитория):

```bash
dotnet user-secrets set "Jwt:Key" "<значение>" --project backend/src/Sitora.WebApi
```

На этой машине user secrets уже заданы, поэтому достаточно:

```bash
cd backend/src/Sitora.WebApi
dotnet run
```

Затем откройте http://localhost:5194 — это сайт (страницы из `frontend/`), Swagger — на http://localhost:5194/swagger. `dotnet watch run` открывает браузер сам. В Development миграции и данные сидера применяются при старте. Чтобы вызвать закрытые методы, войдите через `POST /api/v1/auth/login` (пароли сидера — `SEED_*_PASSWORD` в `.env`), скопируйте `accessToken` и вставьте его в **Authorize**.

**Тесты:**

```bash
dotnet test
```

По умолчанию тесты поднимают PostgreSQL через Testcontainers (нужен Docker). Без Docker задайте `SITORA_TEST_DB` — строку подключения к своему серверу с правом создавать базы.

**Команда миграций** (в Production — обязательна перед стартом API):

```bash
dotnet Sitora.WebApi.dll --migrate
```

Она применяет миграции, создаёт роли и первого админа из `BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD` (в Development — ещё и данные сидера), после чего завершается.

**Переменные окружения** (только имена):
- `ConnectionStrings__Default`, `Jwt__Key`, `Encryption__Key`, `ASPNETCORE_ENVIRONMENT`, `AllowedHosts`;
- `Cors__AllowedOrigins__0`, `Cors__AllowedOrigins__1`;
- `ForwardedHeaders__Enabled`, `Database__MigrateOnStartup`, `Storage__RootPath`, `Hangfire__ServerEnabled`;
- `RateLimiting__LoginPerMinute`, `RateLimiting__SmsPerHour`, `RateLimiting__PublicFormsPerHour`, `RateLimiting__AnonymousPerMinute`, `RateLimiting__UserPerMinute`;
- `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD`;
- `SEED_ADMIN_PASSWORD`, `SEED_MANAGER_PASSWORD`, `SEED_ACCOUNTANT_PASSWORD`, `SEED_CONTENT_PASSWORD`;
- `SITORA_TEST_DB` — только для тестов.

В compose-файлах значения берутся из `.env` (образец — `.env.example`): `POSTGRES_PASSWORD`, `JWT_KEY`, `ENCRYPTION_KEY`, `API_DOMAIN`, `SITE_ORIGIN`, `CRM_ORIGIN`, `BOOTSTRAP_ADMIN_*`, `SEED_*`.

**Для разработки в Docker** (не проверено):

```bash
docker compose up -d --build
```

**Деплой на VPS** (не проверено): пошагово в `docs/DEPLOY.md`.
1. `.env` по образцу.
2. Сборка и миграции:

   ```bash
   docker compose -f docker-compose.prod.yml build migrate
   docker compose -f docker-compose.prod.yml run --rm migrate
   ```

3. Запуск:

   ```bash
   docker compose -f docker-compose.prod.yml up -d
   ```

4. Проверки из раздела 4 инструкции. Бэкапы — `scripts/backup.sh` по cron, восстановление — `scripts/restore.sh`.

## 10. Что нужно сделать вам

1. **WSL и Docker Desktop.** Установить WSL (`wsl --install` от администратора, перезагрузка) и запустить Docker Desktop. После этого проверить `docker compose up`, сборку образа, сервис `migrate` и тесты через Testcontainers.
2. **Репозиторий на GitHub.** Создать его и отправить туда код — тогда впервые запустится CI.
3. **Telegram.** Создать бота и передать токен бота и ID чата менеджеров. Тогда можно подключить настоящую отправку вместо заглушки.
