# Принятые решения

- Решение в формате `Sitora.sln` (шаблон .NET 10 по умолчанию создаёт `.slnx`, но в ТЗ указан `.sln`).
- Domain подключает только `Microsoft.Extensions.Identity.Stores`, чтобы `AppUser` наследовал `IdentityUser<Guid>`; EF Core и HTTP в Domain нет.
- Роли хранятся в таблицах Identity (`Roles`, `UserRoles`), а не отдельным полем `Role` в `Users`; таблицы Identity переименованы без префикса `AspNet`.
- Добавлено пятое исключение домена `UnauthorizedException` (→ 401) для неверного входа и истёкшей сессии.
- Refresh-токен: 64 случайных байта, в базе только SHA-256 хеш, срок 30 дней, ротация при каждом обновлении; повторное использование старого токена отзывает все сессии пользователя.
- `POST /auth/logout` принимает refresh-токен в теле и не требует access-токена; повторный выход отвечает 204.
- Добавлен `GET /api/v1/auth/me` для проверки токена и получения текущего пользователя.
- Вход блокируется на 15 минут после 5 неудачных попыток (lockout Identity).
- В JWT роли лежат в claim `role`, идентификатор пользователя в `sub` (`MapInboundClaims = false`).
- Миграции в Development и Staging применяются при старте; в Production — только командой `--migrate` (изменено при доработках по новому ТЗ, см. ниже). Роли создаются всегда, пользователи сидера только в Development.
- Если переменная с паролем пользователя сидера не задана, пользователь не создаётся, в лог пишется предупреждение.
- Swagger включён во всех окружениях, кроме Production.
- `Microsoft.EntityFrameworkCore.Design` и фабрика контекста для `dotnet ef` лежат в Infrastructure; `dotnet-ef` установлен локальным инструментом (`dotnet-tools.json`).
- PostgreSQL из docker-compose проброшен на порт 5433, чтобы не конфликтовать с локальным сервером на 5432.
- Тесты используют Testcontainers (`postgres:18`); если Docker недоступен, можно задать `SITORA_TEST_DB` со строкой подключения к своему серверу — тесты создадут и удалят временную базу.

## Этап 2. Каталог и заявки

- `Building.FloorsCount` — число жилых этажей; коммерческий этаж 0 существует отдельно, номер этажа допустим от 0 до `FloorsCount`.
- Каталог отдаёт этаж 0 вместе с жилыми (флаг `isCommercial`), поэтому у «Sitora Residence» 17 этажей: 16 жилых по 8 квартир (128) и коммерческий без квартир.
- Номер квартиры — целое число; в сидере это `этаж × 100 + позиция` (101…1608). Уникальность — `(FloorId, Number)`, как в ТЗ.
- Студия хранится как `Rooms = 0`.
- Цена квартиры везде округляется до 100 сомони (не только в сидере), чтобы правило было одно; валюта каталога — TJS.
- Статус квартиры — `private set` в сущности, менять его можно только методами `Book`, `ReleaseBooking`, `Sell`, `SetOnRequest`.
- «Под запрос» включается и выключается отдельным `PATCH /apartments/{id}/on-request` (Content, Admin), только из статуса Free и обратно; через PUT статус не меняется.
- Сидер ставит квартирам только Sold, Free и изредка OnRequest; статус Booked без записи брони был бы несогласованным, поэтому брони появятся в сидере на этапе 3.
- Перечисления хранятся в базе строками (нужно для частичного индекса брони по `Status = 'Active'`).
- Пагинация: `page` от 1, `pageSize` по умолчанию 20, максимум 100; неверные значения приводятся к допустимым без ошибки.
- Кэш каталога — `IMemoryCache` на 30 секунд; любое изменение каталога или статуса сбрасывает весь кэш каталога сразу. Кэш живёт в памяти процесса, при нескольких экземплярах API понадобится Redis.
- Язык названия дома выбирается по `Accept-Language` (`tg` → `NameTg`, иначе `NameRu`); в ответе также есть оба варианта для CRM.
- Импорт Excel: первый лист, строка заголовков, столбцы этаж, номер, комнат, площадь, цена за м². Недостающие этажи создаются, существующие квартиры обновляются, статусы не импортируются. При любой ошибке ничего не сохраняется, ответ 422 со списком ошибок по строкам. Лимит файла 5 МБ.
- Аудит (`IAuditService`) сделан уже на этапе 2, чтобы писать изменения цен; запись сохраняется в той же транзакции, что и изменение. Просмотр аудита — этап 3/Admin.
- `Notification.UserId` может быть пустым: так записываются сообщения в общий канал менеджеров.
- Telegram-заглушка (на этом этапе; позже заменена настоящим `TelegramNotifier`, Bot API) пишет сообщение в лог Serilog и в таблицу `Notifications`. Сбой отправки не отменяет заявку: заявка сохраняется раньше уведомления.
- Телефон нормализуется к `+992XXXXXXXXX`; принимаются 9 цифр или 12 с кодом 992. Номера других стран пока не принимаются.

## Этап 3. Бронь и CRM

- Admin входит во все наборы ролей: эндпоинты «для Manager» доступны и Admin.
- Двойная бронь исключается дважды: строка квартиры блокируется `SELECT … FOR UPDATE` в транзакции, и частичный уникальный индекс `IX_Bookings_ApartmentId_Active` не даёт записать вторую активную бронь. Оба случая отвечают 409.
- Те же блокировки берут продление, отмена, снятие брони задачей и операции сделки, чтобы они не пересекались.
- Гостевая бронь создаёт заявку (или берёт открытую заявку с тем же телефоном). Гость не может держать больше одной активной брони на номер; менеджер — без ограничения.
- Бронировать на существующего клиента (`customerId`) может только Manager/Admin, гость получает 403.
- Продление добавляет 48 часов к более позднему из «окончание брони» и «сейчас». Отмена требует причину.
- Hangfire использует то же хранилище PostgreSQL (схема `hangfire`). Дашборд Hangfire не включён: у него своя авторизация через cookie, а в API только JWT.
- Сервер Hangfire выключается переменной `Hangfire__ServerEnabled=false` (так делают тесты и можно делать на лишних экземплярах API).
- Добавлен этап сделки `Cancelled` («Отменена»): без него брошенная сделка навсегда занимала бы квартиру. `Completed` и `Cancelled` — конечные, этап после них не меняется.
- На квартиру допускается одна неотменённая сделка (частичный уникальный индекс `IX_Deals_ApartmentId_Open`).
- Сделка держит квартиру с этапа «Бронь» (Booked) и продаёт с «Договора» (Sold). При возврате назад квартира возвращается в Booked или Free; для этого добавлен переход Sold → Booked (`RevertSale`).
- Если на квартире активная бронь этого же покупателя (по клиенту или по телефону заявки), сделка забирает её: бронь становится Converted, сделка начинается не раньше «Брони», заявка закрывается. Бронь другого человека — 409.
- Сделки пока только в TJS; USD отклоняется (422) до этапа 4, где появится курс НБТ.
- Скидка: от 0 и меньше цены, при скидке больше нуля нужна причина. Меняется только при создании сделки.
- Менеджеры видят все сделки и заявки (одна команда продаж), не только свои.
- Клиента можно завести из заявки (`leadId`): заявка становится Converted, её активные брони переходят на клиента.
- Паспортные данные шифруются AES-256-GCM ключом `Encryption__Key` (32 байта, base64) и отдаются только в карточке клиента (`GET /customers/{id}`), не в списке и не в аудите.
- `/crm/pipeline`: колонки по этапам от «Заявки» до «Завершена». В «Заявке» также открытые заявки без активной брони, в «Брони» — активные брони без сделки. До 50 карточек на колонку, `count` — полное число.
- `GET /audit` (Admin): фильтры `entity`, `entityId`, `from`, `to`, сортировка от новых к старым.
- Сидер: 10 клиентов, 5 сделок на этапах Lead…Payment на свободных квартирах верхних этажей, 2 брони с сайта на 48 часов. Пароли и паспорта выдуманные.
- `Newtonsoft.Json` закреплён на актуальной версии: Hangfire по умолчанию тянет 11.0.1 с известной уязвимостью.
- Пользователи (`GET`/`POST /users`) в ТЗ не привязаны к этапу; сделаны на этапе 4 вместе с учётными записями покупателей.

## Этап 4. Кабинет покупателя

- Вход по SMS только для тех, кто уже есть в клиентах (по телефону). Ответ `sms/send` одинаковый для любого номера (202), чтобы по нему нельзя было узнать, кто покупатель; SMS уходит только клиентам.
- Код: 6 цифр, живёт 5 минут, 5 попыток ввода; в базе хранится SHA-256 от «телефон:код». Не больше 5 кодов в час на номер, дальше 429.
- При первом входе создаётся пользователь с ролью Customer (логин — телефон, без пароля) и привязывается к клиенту.
- `RequireUniqueEmail` в Identity выключен (у покупателей нет почты); уникальность почты держит частичный уникальный индекс `EmailIndex`.
- Ошибки Identity (пароль и т. п.) переведены на русский (`RussianIdentityErrorDescriber`).
- `POST /users` создаёт только сотрудников (Admin, Manager, Accountant, Content); пароль задаёт администратор.
- Покупатель получает список своих сделок через `GET /me/deals`; график, документы и акт сверки — по общим адресам `/deals/{id}/...`. Для чужой и несуществующей сделки ответ одинаковый — 404. Content к сделкам доступа не имеет (403).
- «Сотрудник» в правах на график, документы и акт сверки — это Manager, Accountant и Admin.
- График: день платежа 1–28 (чтобы он был в каждом месяце), срок 1–360 месяцев, взнос от 0 до 100% не включая 100. Взнос — в дату начала, месячные платежи — с месяца после неё. Взнос и месячный платёж округляются до целой единицы валюты договора (сомони или доллар), остаток округлений — в последнем платеже.
- Пересоставить график можно, только пока по сделке нет платежей. Составляет график Manager (как в ТЗ) и Admin.
- Распределение оплат не хранится отдельно от платежей: после каждого платежа или сторно все пункты графика пересчитываются от общей оплаченной суммы, начиная с самых ранних.
- Платёж без графика не принимается (422); сумма сверх остатка по договору — тоже; дата оплаты — календарная дата по Душанбе, не в будущем.
- Сделки в USD включены: цена = цена квартиры в сомони ÷ курс на сегодня, округление до 1 доллара; без курса — 422.
- Пересчёт платежа: берётся курс USD на дату оплаты или ближайший более ранний (НБТ не публикует курс в выходные). `RateUsed` хранится, если хоть одна из валют — USD; для сомони к сомони он пустой. Сохраняются сумма в валюте платежа, в валюте договора и в сомони.
- Сторно копирует суммы и курс исходного платежа с обратным знаком, датой ставится день исправления. Сторнировать можно один раз (уникальный индекс по `ReversalOfId`), сторно сторнировать нельзя.
- Платежи и сторно по одной сделке идут по очереди (блокировка строки сделки `FOR UPDATE`).
- Курс: ручной ввод `PUT /rates` (Accountant, Admin) на дату не дальше завтрашней; повторный ввод на ту же дату перезаписывает. Курс хранится с 4 знаками. `GET /rates/current` открыт всем.
- Задача `update-rates` (каждый день 05:00 UTC = 10:00 Душанбе) вызывает `IRateProvider`; на этом этапе это была заглушка (позже — `NbtRateProvider`, XML nbt.tj). Загруженный курс не перезаписывает введённый вручную.
- Курс USD в сидер не добавлен, чтобы не выдумывать банковские данные; сделки сидера — в сомони.
- Документы: PDF, PNG, JPG, DOCX до 20 МБ, тип проверяется по первым байтам файла. Загружают Manager, Accountant, Admin; смотрят и скачивают владелец сделки и они же. Файлы лежат в `Storage:RootPath` (в Docker — том `files`), ключ формирует сервер.
- Акт сверки: на дату `?date=YYYY-MM-DD` (по умолчанию сегодня по Душанбе). Начислено — сумма пунктов графика со сроком до этой даты, оплачено — платежи и сторно до этой даты в валюте договора, задолженность — начислено минус оплачено (не меньше нуля), остаток — сумма договора минус оплачено.
- PDF строится QuestPDF под Community-лицензией (бесплатна для компаний с годовой выручкой до 1 млн долларов — перед продакшеном проверить, подходит ли застройщику). Шрифт — встроенный в QuestPDF Lato: в нём есть кириллица и таджикские буквы, системные шрифты не нужны.
- О новом платеже и документе покупателю отправляется уведомление через `INotificationSender` (тогда — Telegram-заглушка, сейчас — `TelegramNotifier`), если у клиента уже есть учётная запись.
- SMS-заглушка пишет в лог текст вместе с кодом — это нужно для разработки. Перед продакшеном её нужно заменить настоящим провайдером.

## Этап 5. Стройка и чат

- У этапа стройки есть порядок (`SortOrder`) и процент 0–100 (ещё и проверка в базе). Общая готовность дома — среднее процентов этапов, округлённое до целого.
- Добавлен `POST /buildings/{id}/stages` (Content, Admin): в ТЗ есть только PUT, а этапы нужно как-то создавать.
- Ход стройки видят сотрудники (Manager, Accountant, Content, Admin) и покупатели, у которых есть неотменённая сделка в этом доме; остальным покупателям — 404. Гостям не виден (в ТЗ — «покупатель, Content»).
- Фото: PNG или JPG до 10 МБ, тип проверяется по первым байтам (общая проверка с документами — `FileTypes`). В ответе этапа — готовый адрес фото (с доработок по новому ТЗ это подписанная ссылка, см. ниже).
- Чат: по одной ветке на сделку, писать могут владелец сделки и Manager, Accountant, Admin. У сообщения хранится сторона (`FromCustomer`); при чтении истории сообщения другой стороны отмечаются прочитанными (`ReadAt`).
- История — от новых к старым, постранично. Длина сообщения 1–2000 символов.
- SignalR-хаб `/hubs/chat`: `JoinDeal(dealId)` с проверкой доступа (чужая сделка — ошибка «Сделка не найдена»), `SendMessage(dealId, text)`, событие `messageReceived`. Сообщения, отправленные через REST, тоже рассылаются в хаб.
- Токен для хаба можно передать в `access_token` строки запроса (браузер не ставит заголовок для WebSocket); это принимается только для путей `/hubs`. Serilog пишет в лог путь запроса без строки запроса, токен туда не попадает.
- Пользователь в вызовах хаба берётся из `Context.User` (класс `HubCaller`), а не из `HttpContext`.
- О новом сообщении второй стороне уходит уведомление: от покупателя — в общий канал менеджеров, от сотрудника — покупателю лично.
- SignalR пока работает внутри одного экземпляра API. Для нескольких экземпляров понадобится backplane (Redis).
- Сидер: 8 этапов стройки «Sitora Residence» с примерными процентами, без фото.

## Этап 6. Запуск

- Лимиты запросов — встроенный `RateLimiter` ASP.NET Core, фиксированное окно на IP: вход и refresh — 10 в минуту, `sms/send` и `sms/verify` — 20 в час, заявки и гостевые брони — 30 в час (сотрудники с токеном не ограничены). Значения — в `RateLimiting:*`. Лимит 5 кодов в час на номер остаётся в сервисе.
- Лимиты хранятся в памяти процесса; при нескольких экземплярах API их нужно переносить в Redis.
- HTTPS завершает Caddy (`docker-compose.prod.yml`, `deploy/Caddyfile`): он сам получает сертификат и редиректит HTTP. Приложение в Production добавляет HSTS на 1 год и `UseHttpsRedirection` на случай обращения в обход прокси.
- `X-Forwarded-For/Proto` принимаются только при `ForwardedHeaders__Enabled=true` и от одного прокси; в prod-compose API не открыт наружу. Без этого IP для лимитов был бы IP Caddy.
- CORS: `Cors:AllowedOrigins`, с `AllowCredentials` (его требует клиент SignalR в браузере). В Development разрешены `localhost:3000` и `localhost:5173`.
- Защитные заголовки — свой небольшой middleware; заголовок `Server` убран в Kestrel.
- Первый администратор вне Development создаётся из `BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD`, только если админов ещё нет.
- Добавлен `PATCH /users/{id}/status` — блокировка сотрудника с отзывом его refresh-токенов (нужно, чтобы уволенный сотрудник терял доступ).
- SMS-заглушка вне Development не пишет код в лог, только маскированный номер.
- Логи в Production — JSON в stdout (компактный формат Serilog), их собирает docker.
- Бэкап: `pg_dump --format=custom` из контейнера базы и tar папки файлов из контейнера API, хранение 14 дней, временные файлы, чтобы недописанный бэкап не выглядел готовым. Восстановление — `pg_restore --clean` с остановкой API и подтверждением.
- `.gitattributes` закрепляет LF для `.sh`, `Caddyfile`, `*.yml` и `Dockerfile`: с CRLF они не работают на Linux.
- Образ Caddy — `caddy:2` (последний второй мажор); PostgreSQL — `postgres:18`, как в ТЗ.
- Деплой и Docker не проверены на чистой машине: на машине разработки нет WSL, VPS нет. Это записано в README как известное ограничение.

## Доработки по новому ТЗ (D:\Downloads\TZ.md)

- Миграции — отдельной командой при деплое: `dotnet Sitora.WebApi.dll --migrate` применяет миграции, создаёт роли, первого админа (и в Development — данные сидера) и выходит, не поднимая сервер. В Production API сам миграции не применяет (`Database:MigrateOnStartup` по умолчанию `false`) и при неприменённых миграциях не стартует с подсказкой команды. В prod-compose команду выполняет сервис `migrate`, API ждёт его успешного завершения.
- График показывает эквивалент во второй валюте (TJS ↔ USD) по текущему курсу — последнему не позже сегодняшнего дня — с пометкой «оценочно» (`Equivalent` в ответе и `AmountDueEquivalent`/`AmountPaidEquivalent` у пунктов). Без курса эквивалента нет (`null`). Суммы к оплате и распределение платежей не меняются: платёж по-прежнему пересчитывается по курсу на дату оплаты.
- PDF графика платежей: `GET /deals/{id}/schedule.pdf`, права как у графика. Данные те же, что в `GET /deals/{id}/schedule` на сегодня: пункты со статусами, итоги и, если введён курс, колонка оценочного эквивалента со сноской. Шапка сделки общая с актом сверки.
- Описание дома на двух языках: `DescriptionRu` (бывший `Description`, миграция переименовывает столбец, данные сохраняются) и `DescriptionTg`. В ответе `description` — на языке `Accept-Language`; если таджикского описания нет, отдаётся русское. Название дома по-прежнему обязательно на обоих языках. Перевод описания для сидера не выдуман: `DescriptionTg` там пустой.
- `PlanCoords` из ТЗ сделан как `PlanSlot` (обязательная позиция 0–7 на плане этажа, уникальна в пределах этажа, проверка в базе) и необязательный `Model3dId` (до 100 символов). Задаются при создании и правке квартиры и в импорте (столбцы F и G). Пустой G при импорте не стирает уже заданный `Model3dId`. Обмен двух квартир позициями нужно делать в два шага: уникальность проверяется после каждой строки.
- Миграция `ApartmentPlanSlot` назначает уже существующим квартирам позиции по порядку номеров на этаже; этаж больше чем с 8 квартирами остановит миграцию — его нужно разметить вручную. Обе ручные правки миграций (описание и позиции) проверены тестом на существующих данных.
- В сидере позиция = номер квартиры на этаже − 1, `Model3dId` пустой.
- CI — GitHub Actions (`.github/workflows/ci.yml`): сборка с `--warnaserror`, все тесты через Testcontainers (на раннере GitHub есть Docker), сборка Docker-образа без публикации и `docker compose config` для обоих compose-файлов. Деплой из CI не делается: сервер и секреты пока не заданы. Результаты тестов сохраняются как артефакт при падении.
- Файлы отдаются только по подписанным ссылкам на 15 минут (`GET /api/v1/files?token=…`, без входа). `GET /documents/{id}/download` теперь проверяет права и возвращает `{ url, expiresAt }`, а не сам файл; у фото в ответе этапа стройки `url` — такая же ссылка (её можно ставить в `<img src>`, где браузер не отправляет JWT). Старый `GET /construction/photos/{id}` убран.
- Токен: `тип.id.срок` и HMAC-SHA256. Ключ выводится из `Jwt__Key` (HMAC с меткой назначения), поэтому отдельный секрет не нужен, но ключи JWT и ссылок разные. Ссылку не отозвать досрочно — она истекает сама. Токен в строке запроса, чтобы не попадать в лог Serilog. Url относительный: адрес API клиент добавляет сам.
- Отчёты бухгалтера (в ТЗ состав не расписан, взят минимальный набор): поступления за период (`/reports/payments`, по умолчанию текущий месяц, не больше 366 дней; платежи и сторно с минусом, итоги по валюте платежа и в сомони) и задолженность на дату (`/reports/debts`, по умолчанию сегодня; распределение по графику пересчитывается по платежам до этой даты, отменённые сделки не учитываются). Обе — JSON и `.xlsx`. Доступ — Accountant и Admin. Без пагинации: объём ограничен периодом или датой.
- Health-check: `/health/live` без проверок (для контейнера), `/health/ready` и `/health` — база, запись в хранилище файлов и (где запущен) сервер Hangfire; отказ фоновых задач — `Degraded`, а не 503, потому что API продолжает отвечать. В ответе только имена и статусы проверок. `/health*` не перенаправляется на HTTPS, чтобы его можно было опрашивать по HTTP внутри сети docker.
- Проверка контейнера — режим `dotnet Sitora.WebApi.dll --healthcheck` (в образе нет curl): запрос к `/health/live` с доменом из `AllowedHosts` в заголовке Host.
- Оповещение о сбое: задача Hangfire `health-alert` раз в 5 минут проверяет `ready` и сообщает в канал менеджеров только при смене состояния. Состояние хранится в памяти: после перезапуска API первое сообщение может повториться. Полное падение процесса так не обнаружить — нужна внешняя проверка (см. DEPLOY.md, «Мониторинг»).
- Логи в Production: Serilog в stdout и в файлы `logs/sitora-ГГГГММДД.log` (JSON, по дням или по 100 МБ, хранятся 14 файлов, том `logs`). В записи о запросе — `ClientIp` и `UserId`; запросы к `/health` пишутся только на уровне Verbose, ошибки — всегда. Seq не подключён: ТЗ допускает «файлы или Seq».
- Блокировка после неудачных входов (5 ошибок — 15 минут, Identity) дополнена: для несуществующей или отключённой почты ведётся такой же счётчик в памяти и тратится время на проверку фиктивного хеша, поэтому по ответу и задержке не понять, существует ли учётная запись. Разблокировка администратором (`PATCH /users/{id}/status` с `isActive: true`) снимает и временную блокировку входа. Счётчик для несуществующих почт живёт в памяти процесса.
- Общий лимит запросов (`GlobalLimiter`) поверх политик входа, SMS и форм: гости — `RateLimiting:AnonymousPerMinute` (300) на IP, вошедшие — `RateLimiting:UserPerMinute` (600) на пользователя; `/health*` не ограничивается.
- При старте API проверяет обязательные секреты (`ConnectionStrings__Default`, `Jwt__Key`, `Encryption__Key`; для `--migrate` — только строку подключения, в Development ещё ключ шифрования для сидера) и при нехватке пишет одну строку со списком всех недостающих переменных, код выхода 1, без стека исключения.
- Для локальной разработки секреты можно хранить в user secrets (`dotnet user-secrets`, `UserSecretsId` в `Sitora.WebApi.csproj`, сами значения — в профиле пользователя вне репозитория). ASP.NET читает их только в Development, поэтому `dotnet run` работает в любом окне без переменных окружения. Переменные окружения имеют приоритет над user secrets; в Staging и Production используются только они. Тесты задают свои настройки с наивысшим приоритетом и от user secrets машины не зависят.

## Организации, роли и вход по коду из почты

- **Организация** (застройщик) — новая сущность. Ей принадлежат дома, сотрудники (`Users.OrganizationId`), клиенты, заявки, ручной курс и аудит. Остальное (этажи, квартиры, брони, сделки, графики, платежи, документы, чат, этапы и фото стройки) привязано к организации через дом.
- **Где работает фильтр доступа.** Глобальные фильтры EF Core в `AppDbContext` применяются к каждому запросу к базе, а не только в контроллерах. Область доступа берётся из claims токена: `org`, `bld` (дома; нет claim — все дома организации) и `imp`.
  - Без ограничений: гость, покупатель (свои сделки он видит по проверкам владельца, как раньше), фоновые задачи, PlatformOwner вне режима «как владелец».
  - Ограничены: сотрудники и режим «как владелец».
  - `IgnoreQueryFilters()` используется только при входе и в блокировках `FOR UPDATE`. Блокировке перед этим предшествует проверка видимости обычным запросом.
- **Чужое отвечает 404**, как несуществующее, поэтому нельзя узнать, есть ли у другой организации такой id. 403 бывает только там, где закрыта сама роль.
- **Роли.**
  - `Admin` переименован в `Owner` миграцией, у существующих пользователей роль сохраняется.
  - Новые роли — `PlatformOwner` и `ObjectAdmin`.
  - Manager, Accountant и Content остались ролями Identity, но работают как должности внутри организации и её домов.
  - Главная роль в ответе (`role`) выбирается по приоритету PlatformOwner > Owner > ObjectAdmin > Manager > Accountant > Content > Customer.
- **Права руководителей.**
  - ObjectAdmin ведёт свой дом наравне с владельцем: каталог, продажи, деньги, документы, стройка, сотрудники дома.
  - Не может: создавать дома, менять дома сотрудникам, смотреть аудит, трогать руководителей.
  - Аудит пока не разделён по домам, поэтому `/audit` открыт только Owner (и PlatformOwner в режиме).
- **Права меняются со следующего входа.** Состав домов читается из токена. После `PUT /users/{id}/buildings` все refresh-токены сотрудника отзываются, а текущий access-токен доживает свои 15 минут.
- **Клиенты по организациям.** Телефон уникален в пределах организации: один человек может быть клиентом двух застройщиков. Учётная запись покупателя одна на почту и привязывается ко всем его карточкам. Сделку можно оформить только на клиента той же организации, что и квартира.
- **Вход по почте** для всех.
  - Код хранится хешем (SHA-256 с почтой) вместе с `RequestIp`.
  - На каждый запрос создаётся запись, даже для незнакомой почты (`Sent = false`). Поэтому ответ и лимиты одинаковы, и по ним нельзя узнать, есть ли учётная запись.
  - Действует только последний код.
  - Лимит на IP проверяется, только когда IP известен.
- **SMS-вход** не удалён, а выключен: `Auth:SmsLoginEnabled=false`, адреса отвечают 404. Вход по паролю (`Auth:PasswordLoginEnabled`) пока оставлен для сотрудников с паролями. PlatformOwner так не входит.
- **PlatformOwner.**
  - Создаётся только из `ADMIN_EMAIL` и `ADMIN_PASSWORD` (`--migrate`, в Development — при старте). Без пароля не создаётся: второго фактора не было бы.
  - Если почта уже принадлежит пользователю без организации, ему добавляется роль.
  - Второй фактор — пароль (с блокировкой Identity после 5 ошибок) или TOTP после `/platform/totp/enable`.
  - Вызов второго шага живёт 5 минут в памяти процесса. При нескольких экземплярах API нужен общий кеш или «липкие» сессии.
- **Режим «как владелец».**
  - Выдаётся access-токен без refresh: `sub` — сам создатель платформы, роль `Owner`, `org` — выбранная организация, `imp` — его id.
  - Автор в аудите — настоящий человек, а `ImpersonatedById` помечает режим.
  - Middleware дополнительно пишет каждый изменяющий запрос, даже неудачный, с настоящим кодом ответа.
- **Курс по организациям.** Ручной курс бухгалтера действует только в его организации. Курс НБТ общий (`OrganizationId = null`). Если на одну дату есть оба, побеждает ручной курс организации.
- **Заявка с сайта** получает организацию из квартиры или дома. Если ни того ни другого нет, а организация на платформе одна, заявка уходит ей, иначе 422.
- **Миграция `MultiTenancy` не теряет данные:**
  - создаёт организацию по умолчанию (`slug = sitora`; с 08.11.2026 — `nekruz`, миграция `RenameDefaultOrganizationSlug`);
  - переносит в неё дома, клиентов, заявки, аудит и сотрудников;
  - заполняет дом заявки по квартире;
  - нормализует почты клиентов.
- **Приглашения.**
  - Токен — 32 случайных байта, в базе хранится хеш, срок 7 дней.
  - Новое приглашение на ту же почту отзывает прежнее.
  - Принять можно один раз, и только если пользователя с такой почтой ещё нет.

## «Зелёная» часть платформы (конкурс «Идеяи ман — калиди фардо», номинация «Лучшая зелёная бизнес-модель», 14.11.2026)

Главное правило — ничего не выдумывать: на сайте только то, что посчитано из данных платформы или задано застройщиком
с источником. Нет данных — нет блока (без «—» и заглушек).

- **Эко-паспорт дома** — owned-тип `BuildingEcoInfo` в таблице `Buildings` (столбцы `Eco*`), все поля необязательные.
  Правят контент-менеджер и руководители (`PUT /buildings/{id}/eco`), запись в аудит (`EcoUpdated`), сброс кэша каталога.
  В ответе — только заполненные поля; булевы «возможности» на сайте показываются, только если `true`.
- **Тарифы и коэффициенты** — owned-тип `OrganizationGreenSettings` (столбцы `Green*`), правят руководители организации
  (`/owner/green-settings`). Тариф — ставка с 4 знаками (`decimal(18,4)`), деньги в расчёте — до дирамов.
  У «типового дома» и у коэффициента CO₂ источник обязателен (валидация).
- **Калькулятор расходов** — `UtilityCalculator`: кВт·ч в год = площадь × расчётное потребление дома; стоимость =
  кВт·ч × тариф, до 2 знаков, половина — от нуля (как в остальном коде); в месяц — годовое / 12. Без тарифа или без
  расчётного потребления дома — 204, калькулятор не показывается.
- **Бумага: 5 г на лист.** Лист A4 — 0,0625 м²; бумага 80 г/м² → 0,0625 × 80 = 5 г. Это физика, не оценка.
  `paperKgSaved = pagesSaved × 0,005`.
- **Страницы** — из самого PDF: `/Count` корневого узла `/Type /Pages` (`PdfPages`). Загруженный PDF — при загрузке
  (`Document.PageCount`), выданный онлайн (график, акт сверки) — при выдаче (`IssuedPdf`). Не определилось — `null`,
  и такой файл в страницы не считается (не угадываем; старые документы до этой версии тоже не считаются).
- **CO₂ — коэффициент не задан.** Для пересчёта «кг бумаги → кг CO₂» опубликованные оценки сильно различаются (зависят
  от сырья, страны, энергии комбината), а проверенный источник с конкретной цифрой мы не подобрали. Поэтому по умолчанию
  коэффициента нет, и CO₂ на сайте не показывается. Застройщик может задать его в CRM → Настройки вместе со ссылкой
  на источник — тогда CO₂ появится, а источник выводится под цифрой. Демо-данные коэффициент тоже не задают.
- **«Действия без визита в офис»** — брони с сайта (заявка с источником `Website`), оплаченные онлайн платежи
  (`OnlinePayments.Status = Paid`), сообщения в чате сделки. Подписанные документы не считаются: `SignedAt` — дата
  подписания (обычно бумажного) документа, онлайн-подписи в системе нет. В «километры» и «литры бензина» не переводим —
  таких данных нет.
- **Демо-данные** помечаются флагом организации `GreenIsDemo` (бейдж «Демо-данные» на сайте). Значения
  (`GreenDemoSeeder`, тот же блок в `seed.sql`): класс A, тариф 0,29 TJS/кВт·ч, типовой дом 180 кВт·ч/м² в год с
  источником «Демо-значение…» — правдоподобные, но не официальные.
- **Демо-доступ для жюри** — только при `SEED_DEMO_ACCOUNTS=true`, пароли — только из секретов. Демо-покупатель входит
  паролем лишь при `Auth__DemoPasswordLogin=true` (у жюри нет доступа к его почте), остальные покупатели — по коду.
  Демо-менеджер — роль `Manager` + `DemoReadOnlyMiddleware`: только просмотр и чат (не удаляет, не сторнирует,
  не меняет данные).

## 3D-модель дома — «живая витрина» (полноэкранный режим `/apartments#3d`)

- **Один движок.** Всё 3D — в `modeli-3d-bino-script.js` (Three.js r128 с cdnjs). Полноэкранный режим не создаёт вторую
  сцену: тот же контейнер каталога переносится в слой на весь экран (`modeli-3d-rejim-script.js` — только панели).
  Квартира изнутри — `modeli-3d-kvartira-script.js`, подгружается только по кнопке «Посмотреть внутри». Контролы камеры
  написаны сами (CSP: скрипты только `'self'` и cdnjs, `three/examples` с jsdelivr нельзя).
- **Время суток — по реальному солнцу.** Высота и азимут солнца — стандартная формула малой точности (≈ 0,01°) для
  широты и долготы дома (без координат — Душанбе, 38,56° с. ш., 68,78° в. д.) на сегодняшнюю дату, время UTC+5.
  Высота солнца выбирает вид: ≥ 12° — день, 2…12° — день ↔ закат, −6…2° (гражданские сумерки) — закат ↔ ночь.
  Пока солнце над горизонтом, свет идёт из его настоящего направления. **Ориентация модели условная:** фасад со входом
  смотрит на юг — реальной ориентации дома в данных нет. Кнопки День/Закат/Ночь — точки того же ползунка (13:00,
  солнце на 3° над горизонтом, 21:30). Окна ночью горят «случайно, но стабильно» — по seed 7, одинаково при каждом заходе.
- **Окружение — только реальное (OpenStreetMap, ODbL 1.0).** У дома поля `Latitude`/`Longitude` (decimal(9,6)) задаёт
  контент-менеджер (`PUT /buildings/{id}/location`, CRM → Каталог). **Нет координат — нет окружения, меток мест и вида
  «Окружение»** (остаются газон и улица модели). Файл окружения строится заранее скриптом `frontend/tools/context/build.mjs`
  (Overpass API) и лежит статикой в `frontend/data/context-<buildingId>.json` — сайт к Overpass не ходит, `/privacy` не
  меняется. Файл принимается, только если его точка не дальше 150 м от координат дома. Высота соседних зданий —
  тег `height`, иначе `building:levels × 3 м`, иначе 12 м. Атрибуция «© участники OpenStreetMap, ODbL» — в 3D-режиме
  (ссылка на openstreetmap.org/copyright) и в `frontend/data/CREDITS.md`.
- **Расстояния — по прямой.** Сайт считает их сам (формула гаверсинуса) от координат дома до точки места и подписывает
  «по прямой» — это не путь пешком.
- **Высота дома** на метке = этажи × высота этажа. Поле `FloorHeight` (decimal(4,2), 2,4–6 м); не задана — 3,0 м и
  пометка «оценка».
- **Цена в долларах** — по курсу НБТ из API (`/rates/current`), с подписью «оценочно по курсу»; нет курса — нет долларов.
- **Планировки — один источник.** `frontend/js/planirovki-data.js`: 4 типовые планировки в метрах (комнаты-прямоугольники,
  двери между комнатами, вход из прихожей, окна по фасаду, балкон перед фасадом). По ним рисуется 2D-план (`drawFloorPlan`)
  и строится квартира в 3D, по ним же считаются стены для столкновений в «Прогулке». Планировка масштабируется так, что
  сумма комнат и балкона равна площади квартиры из API; на экране — «Планировка типовая, размеры ориентировочные».
  Реальных планировок застройщика в данных нет — когда появятся, их достаточно описать в том же формате.
- **Мебель — пример** из простых коробок и цилиндров (без внешних моделей), подпись «пример расстановки мебели»,
  переключатель «С мебелью / Без мебели». Расставляется у свободной стены (не перед дверью и окном).
- **Прогулка** — камера на высоте 1,6 м, столкновения — окружность 0,28 м против отрезков стен; двери — разрывы в
  стенах, поэтому пройти можно только через них; балкон ограничен перилами.
- **Скорость.** Окна, деревья, полосы разметки — instancing; здания окружения, дороги и зелень — по одной склеенной
  геометрии на слой; `pixelRatio ≤ 2` (на телефоне ≤ 1,5), тень одна (на телефоне карта 1024). Если 3 секунды подряд
  меньше 30 кадров, качество понижается ступенями (без теней → 1 пиксель на точку, без облаков и контуров соседей).
  При выходе из квартиры и при уходе со страницы геометрия, материалы и текстуры освобождаются (`dispose`), контекст
  WebGL отпускается. Тестовый хук — `window.__house3d.state()`.

## AI-помощник для гостей на публичном сайте (19.11.2026)

- **Отдельный эндпоинт, а не `[AllowAnonymous]` на `/ai/chat`.** `POST /public/{orgSlug}/ai/chat` и `GET .../ai/status`
  в своём контроллере и сервисе (`PublicAiAssistant`): у гостя нет роли, сделок и организации в токене, поэтому промпт,
  контекст и лимиты у него свои и не зависят от того, вошёл ли человек. Организация берётся из адреса (slug, как у
  `/public/brand`), а не из токена: вошедший покупатель на публичных страницах получает тот же публичный режим.
  Авторизованный `/ai/chat` не меняется — в кабинете, CRM и на платформе всё как было.
- **Пузырь только по `status.enabled`.** Без ключа Claude сайт не показывает кнопку, которая на любой вопрос отвечала бы
  503. Сайт без `ORG_SLUG` (дома нескольких застройщиков) помощника не показывает: не о каком одном ЖК отвечать.
- **Лимиты.** Ключ платный, а вход не нужен, поэтому три слоя: короткий вопрос (≤ 500 символов), короткая история
  (10 реплик) и короткий ответ (≤ 400 токенов) — цена одного запроса; `AiPublic` по IP — 6 в минуту (разговор человека)
  и 40 в сутки (не дать одному адресу съесть бюджет); `Claude:PublicDailyLimit` (300 в сутки на организацию) — потолок
  расходов, даже если адресов много. Окна IP — цепочка двух fixed-window лимитеров (`RateLimiter.CreateChained`).
  Суточный счётчик организации — в памяти процесса (`PublicAiQuota`): на один экземпляр Render этого достаточно, Redis
  ради него не нужен; после перезапуска счёт начинается заново. При любом из лимитов ответ одинаковый — 429
  `ai_public_busy` «Помощник сейчас занят, напишите менеджеру» и `contacts` организации: гостю важнее, куда написать.
- **Контекст только из базы, общий построитель.** `EstateContext` собирает то, что застройщик сам показывает на сайте
  (каталог, удобства, эко-паспорт, рассрочка, стройка, контакты, курс НБТ); незаполненное не попадает. Тот же текст
  получает покупатель в кабинете — поэтому из `CustomerPrompt` убраны «типовые» удобства и контакты, которые не
  совпадали с базой. Кэш 60 с: вопросы гостей не пересчитывают каталог каждый раз, а свежесть — как у кэша каталога.
  Цены — по свободным жилым квартирам (без коммерческого этажа), диапазон от/до по числу комнат и валюте; часов работы
  в базе нет — контекст так и говорит, модель не придумывает их.
- **История только в браузере.** Сервер её не хранит; роль `system` и другие роли из истории отбрасываются, реплики
  приводятся к чередованию user/assistant (та же функция, что у `/ai/chat`).

## Telegram для покупателей и вход без повторного кода (19.11.2026)

- **Бренд — из базы, без отдельной задачи о бренде.** `PROMPT_REAL_DEVELOPER.md` (контакты сайта из базы) ещё не
  выполнен; решено не ждать его: письма и бот берут имя застройщика из `Organization.Name` (то, что владелец меняет в CRM,
  «Бренд»). Контакты публичного сайта по-прежнему в `tanzimot-api-url.js` — это следующая задача.
- **«Запомнить меня» — скользящая сессия refresh-токенов.** Каждый refresh выдаёт новый токен на полный
  `Jwt__RefreshTokenDays` от этого момента и наследует вход (`SessionId`, дата входа, браузер): без визитов 30 дней —
  выход. Срок **оставлен 30 дней для всех**: покупатель заходит хотя бы раз в месяц (платёж по графику), а 60–90 дней на
  чужом или общем телефоне — лишний риск; настройка общая для сотрудников и покупателей, и сотрудникам длиннее не нужно.
  Повторно предъявленный токен, **заменённый ротацией**, по-прежнему отзывает все сессии (кража); токен, закрытый выходом
  или «Выйти на нём», — просто 401: иначе закрытое устройство одним запросом выкидывало бы и все остальные.
- **Режим cookie: Dual на Vercel → Render, Cookie — на своём домене.** Cookie `sitora_rt` — `SameSite=Strict`, поэтому с
  сайта `binosoz.vercel.app` на API `binosoz-1.onrender.com` (другой сайт, не только другой домен) браузер её не отправит.
  Чтобы отправлял, нужны `SameSite=None; Secure`, CORS с `credentials` и `fetch(..., { credentials: 'include' })`, но это
  cookie третьей стороны: Safari/iOS (ITP) блокирует их по умолчанию, Chrome — в режиме инкогнито и у части
  пользователей. На iPhone «запомнить меня» тогда не работало бы вовсе. Поэтому там остаётся `Dual`: refresh-токен и в
  теле ответа (localStorage), и в cookie. Сайт, который отдаёт сам API (Render, Docker, VPS с Caddy — сайт и API на
  одном домене), — запрос того же сайта: cookie уходит сама, и можно `Auth__RefreshCookie__Mode=Cookie` — токена в
  localStorage нет, XSS его не украдёт. Сайт к этому готов: `refresh()` и `logout()` без токена в теле работают по cookie.
- **Почта на устройстве — только почта.** `sitora.lastEmail` пишется после входа покупателя и стирается «Выйти» и
  «Сменить»; PIN нигде не сохраняется (браузерный менеджер паролей — его дело, `autocomplete=current-password`).
  Код из письма — только при регистрации и «Забыли код?».
- **«Устройства» — вход = сессия, а не токен.** Список — активные токены, сгруппированные по `SessionId`; имя — разбор
  User-Agent («Chrome · Windows»), IP не храним и не показываем (лишние персональные данные). «Это устройство» — claim
  `sid` в access-токене. Закрыть вход — отозвать его refresh: устройство выйдет, когда кончится access (≤ 15 минут).
- **Сообщения покупателю — одна очередь и журнал `BuyerMessages`.** Каждое сообщение — строка «событие × канал» с
  готовым текстом; задача Hangfire `BuyerMessageJob` только отправляет и пишет итог (Sent/Skipped/Failed), повторяя сбой
  через 1, 5, 15 и 60 минут (5 попыток). Та же таблица — журнал для бухгалтера в CRM. Защита от дублей — уникальный
  `DedupeKey` (событие, сделка, срок пункта, канал, получатель): повторный запуск задачи и гонка двух экземпляров
  ничего не дублируют. В тестах очередь синхронная (`InlineBuyerMessageQueue`).
- **Когда напоминать.** За 3 дня, в день срока, на 1-й день просрочки и ещё раз через 6 дней после первого (то есть на
  7-й день), всё — в 10:00 по Душанбе (05:00 UTC). «Через 6 дней после первого», а не «на 7-й день»: просрочка, которая
  появилась сразу старой (график задним числом, сервис спал), получает первое напоминание сейчас, а второе — через неделю,
  а не оба в один день. Бухгалтерам — как раньше, один раз на пункт.
- **Что куда.** Платёжные напоминания — во все каналы (кабинет всегда, Telegram и почта — если подключены и не выключены).
  Остальные события (бронь, этап, платёж принят, документ, сообщение менеджера) — только в Telegram: письмо о каждом
  этапе — это спам. Текст чата в Telegram не уходит («менеджер написал вам»), документ — ссылкой на кабинет, не на файл.
  «Не в сети» — нет в кабинете 2 минуты (по `PresenceTracker`).
- **Отписка без входа — подписанная ссылка, а не таблица токенов.** HMAC от ключа JWT, 90 дней; повторный переход ничего
  не меняет (письма уже выключены), поэтому «одноразовость» здесь не нужна. GET показывает страницу с кнопкой, выключает
  POST: почтовые сканеры, открывающие все ссылки, не отпишут человека сами.
- **Привязка Telegram — билет в кэше на 15 минут.** `POST /profile/telegram/link` кладёт хеш токена в
  `IDistributedCache` (Redis или память) и отдаёт `t.me/<бот>?start=<токен>`; бот по `/start <токен>` сохраняет `chat_id`
  и сразу удаляет билет. Ссылку открывает сам человек (кнопка-ссылка), а не скрипт после запроса — иначе её закрыл бы
  блокировщик всплывающих окон. Webhook проверяет секрет и в адресе, и в заголовке `X-Telegram-Bot-Api-Secret-Token`:
  адрес может попасть в логи прокси, заголовок — нет.
- **Telegram Gateway — наш код, наша проверка.** Код генерирует и проверяет API (как SMS: хеш, 5 попыток, 10 минут), а
  Gateway только доставляет: `checkSendAbility` → `sendVerificationMessage` с тем же `request_id` (повторная проверка не
  оплачивается); `checkVerificationStatus` — сообщить, что код введён. Лимиты — как у кодов из почты, на номер и на IP;
  незнакомому номеру ничего не отправляем (деньги). Суточный лимит на платформу считается от полуночи по Душанбе.
  Номер без Telegram — понятная ошибка «войдите по почте». Подтверждение телефона при регистрации не добавлено: почта
  при регистрации подтверждается всегда, а задача разрешает его не требовать. Старая заглушка SMS не тронута:
  с Gateway вход по телефону идёт через Telegram, без него — как раньше.
- **Отправитель — застройщик.** `EmailMessage.FromName` — имя организации; адрес — `Email__From`. Для реального
  застройщика — свой домен через Resend или SMTP с SPF, DKIM и DMARC (`docs/DEPLOY.md`); Gmail с личного ящика годится
  для начала (лимит Google ~500 писем в сутки).

## ЖК «Rich Tower»: 3 блока на одном участке (26.11.2026, `PROMPT_RICH_TOWER_3BLOK.md`)
- **Название — «Rich Tower» (26.11.2026).** ЖК раньше назывался «Некруз Резиденс». Теперь имя на сайте, в кабинете и в
  письмах берётся из API — это имя организации (`GET /public/brand?slug=…`, `Organization.Name`). Без API, до его ответа,
  в `offline.html` и в `<title>`/meta/OG — «Rich Tower» (ключ `brand.name`, одинаковый в ru/tg/en). `seed.sql` и сидер
  разработки меняют только прежние имена: организацию «Sitora» и «Некруз Резиденс», дом «Некруз Резиденс». Имя, которое
  задал владелец, не трогается. Каждое переименование пишется в AuditLog (`Renamed`). Макет `docs/design/` и разбор
  `docs/exam/` не переписываются — это история проекта.
- **Второй застройщик разработки** (прежний сидер «Rich Tower», slug `rich-tower`) переименован в «Второй застройщик»
  (`second-builder`, `Seed:SecondBuilder`, `SEED_SECONDBUILDER_OWNER_PASSWORD`). Иначе два застройщика с одним именем
  путались бы. Базы разработки, созданные раньше, получают новые имя и slug (AuditLog `Renamed`).
- **Имя менеджера на странице контактов** («Некруз», `CONTACT.manager`) — это человек, а не бренд, поэтому оно остаётся.
  e2e «нет старого бренда» ищет «Некруз Резиденс», «Nekruz Residence» и «НЕКРУЗ». Выдуманные отзывы `rev.r1–r3` и
  `home.proof` в i18n нигде не показывались — удалены.
- **3 блока — это `Building` с буквой (`BlockCode`).** Форма (`Footprint`), место на участке (`SitePosition`) и уступы
  (`Setbacks`) хранятся в jsonb. Это данные, а не код: их меняют в CRM → «Каталог» → блок → «Форма и место на участке»
  (JSON и 2D-предпросмотр). Точка контура — `[x, y]` или `[x, y, r]`: у вершины угол скругляется радиусом r, дуга из 6
  отрезков (`PlanGeometry.Expand`, на сайте `S.geom.expand` — то же самое). Проверки: 3–64 вершины, нет самопересечений,
  площадь больше нуля — в валидаторе; уступ внутри контура, блоки не пересекаются и стоят не ближе
  `Catalog__MinBlockGapMeters` (20 м) — в сервисе. Ошибка — 400 с текстом из `ErrorCatalog` (ru/tg/en).
- **Прежний дом сидера остаётся** («Rich Tower», 20 этажей, без буквы): на нём демо-сделки, «Зелёный эффект» и тесты.
  Три блока A/B/C добавляет `RichTowerBlocksSeeder` в Development. На проде те же блоки создаёт `seed.sql` (см. ниже).
  Если у организации есть блоки, сайт показывает только их (этап 3); дом без буквы остаётся в CRM и кабинете.
- **Сид блоков (концепт).** Блоки стоят буквой «П» вокруг общего двора: A — запад, B — север, C — восток, к улице —
  юг. Разрывы: A–B 26 м, B–C 28 м. A — Г-образный 38 × 34 м со скруглённым внешним углом (r 6 м), 22 этажа. B — 50 × 20 м,
  срезанные торцы и 4 эркера по 5 м, 20 этажей. C — П-образный 42 × 28 м, скруглённые внешние углы (r 8 м), открыт во
  двор (повёрнут на 90°), 20 этажей. Уступ — последний этаж (пентхаусы). План участка: контур 205 × 97 м, мини-футбольное
  поле 42 × 22 м, детская площадка 18 × 14 м, газон, дорожка, рампа паркинга. Площадка и поле есть в удобствах блоков
  (`playground`, `football_field`); 3D рисует зону, только если её удобство есть в данных.
- **Цена — за м² по этажу, валюта USD (этап 2а).** Правило — это данные блока: ступени `PriceSteps` (jsonb, деньги —
  decimal), `PenthousePricePerM2`, `PriceCurrency`. Цена квартиры = площадь × цена м² её этажа с округлением до сотни
  (`Apartment.CalculatePrice`, как раньше). Правило сида: 3–6 этаж — 1 200 $/м²; с 7-го по 19-й — ровно от 1 200
  (6-й этаж) до 900 (19-й), минус 300/13 ≈ 23,08 $ за этаж, цена м² округляется до 1 $. Поэтому ступени записаны как
  3–5 и 6–19 «1 200 → 900». С 20-го и выше, кроме последнего, — 900. Последний этаж — пентхаусы, 1 400 $/м². Скидок и
  акций на сайте нет. «Пересчитать цены» меняет только свободные квартиры, на каждое изменение — `PriceChanged` в
  AuditLog в той же транзакции. Сайт показывает цену в валюте каталога («$ …») и рядом «≈ … TJS по курсу НБТ ·
  оценочно по курсу». Сделка без валюты в запросе — в валюте каталога. Если валюты разные, цена пересчитывается по курсу
  на сегодня: USD → TJS до сомони, TJS → USD до доллара. Оплаты и графики идут в валюте сделки, как раньше.
- **Квартиры типового этажа (этап 2г): 8 на этаж** вокруг лифтового узла (3 лифта и лестница) и коридора. Квартиры
  стоят полосой глубиной 7 м вдоль фасада, по порядку PlanSlot от первой вершины контура по часовой стрелке.
  Площадь полосы — площадь контура минус внутренний контур (сдвиг на 7 м), это коридор и ядро. Площади квартир — доли
  полосы (FloorPlanMath), поэтому сумма квартир, коридора и ядра равна площади этажа (тест: допуск 5 %). Сайт делит
  полосу по тем же площадям (S.geom.floor) и получает те же многоугольники. Набор под форму блока:
  - A (Г): 2 студии, 2 × 1-комн., 1 × 2-комн., 3 угловые/торцевые (4, 4 и 3 комнаты: торцы крыльев и скруглённый угол);
  - B (вытянутый): 2 студии, 2 × 1-комн., 2 × 2-комн. (с эркерами), 2 торцевые 4-комн. со срезанными углами;
  - C (П): 2 студии, 2 × 1-комн., 2 × 2-комн. (во дворе), 2 угловые 4-комн. в скруглениях.
  Угловые и торцевые больше всех остальных квартир этажа, у них окна на две стороны.
- **Магазины, паркинг, лифты (этап 2в).** Вид помещения — Apartment.Kind: Residential, Penthouse, Commercial, Parking
  (миграция ApartmentKinds; у прежних строк — Residential). Бронь, продажа, оплата и AuditLog одни для всех видов.
  Квартирами в счётчиках сайта и API (TotalApartments, FreeApartments) считаются только квартиры и пентхаусы.
  Магазины и машино-места — отдельно: CommercialUnits, ParkingSpots.
  - 1–2 этажи каждого блока — 6 помещений на этаж вдоль фасада (та же полоса 7 м, витрины на улицу), 1 500 $/м²
    (CommercialPricePerM2). Арендаторов и вывесок нет, витрины нейтральные.
  - Паркинг −1 и −2 — **под каждым блоком**, не общий. Так машино-место — помещение своего блока: своя бронь, свои
    этажи −1/−2 и одна разметка в 3D на весь уровень. Общий паркинг под двором потребовал бы отдельного «здания»
    без квартир. По 28 мест на уровень, 2,5 × 5,3 м (13,25 м²), 20 000 $ за место — не от площади
    (ParkingSpotPrice, Apartment.SetFixedPrice). Въезд-рампа — зона parking_ramp плана участка.
  - Нумерация этажей: −2, −1, 1, 2, 3… (в UI — со знаком минус), этажа 0 у блоков нет. PlanSlot — до 99.
  - Лифтов в блоке — Building.ElevatorsCount (сид 3): на сайте «Лифтов: 3», в 3D — шахты в ядре.
- **Пентхаусы (этап 2б).** Последний этаж каждого блока (A — 22-й, B и C — 20-й) — только пентхаусы: 4 на этаж, каждый
  4-комнатный (гостиная-кухня и 3 спальни), всего 12. Это квартиры (Kind = Penthouse): они в счётчике квартир, бронь,
  продажа и оплата — как у квартир. Площадь — доля полосы этажа уступа (Setbacks[].PlanDepth: A и C — 6,5 м, B — 8 м),
  выходит 170–230 м². Терраса — кольцо между контуром блока и контуром уступа, делится по долям площади
  (Apartment.TerraceArea, миграция PenthouseTerrace). **В цену терраса не входит:** цена = площадь × 1 400 $/м², террасу
  карточка показывает отдельно с пометкой: цена за м² пентхауса так одна и понятная покупателю. Коэффициент ×0,3, как у
  балкона, можно ввести, когда застройщик подтвердит, как он считает террасы в договоре. Высоты
  потолка в API нет — сайт пишет «3,6 м (оценка)». У B для террас убраны эркеры последнего этажа, а торцы отступают на 3 м.
- **Переход прода на 3 блока (seed.sql) — прежний дом скрывается с сайта, его деньги не трогаются.** На проде уже
  есть дом «Некруз Резиденс»: 160 квартир в TJS, демо-брони и демо-сделки с платежами в TJS. `seed.sql` (блок
  «Rich Tower blocks», генерирует `RichTowerBlocksSql.cs` из данных сидера) один раз создаёт блоки A/B/C как новые
  `Building`. Все помещения свободны, цены в USD по правилу: продаж и броней скрипт не выдумывает. Если плана участка
  нет, скрипт его задаёт, а прежние дома без буквы скрывает с сайта (`IsPublished = false`, AuditLog `Unpublished`).
  Выбран вариант «скрыть», а не «оставить», даже при сделках в доме: сайт ЖК из трёх блоков и в каталоге — только
  блоки. Скрытие ничего не удаляет и не пересчитывает: квартиры остаются в TJS, сделки, графики и платежи — как были
  (сторно — по-прежнему единственный способ отменить платёж). Повторный запуск ничего не делает: блоки уже есть.
  Вернуть дом на сайт — CRM → «Каталог» → «Показывать дом на сайте» (AuditLog `Published`).
- **Что видит кто, если дом скрыт.** Гость и покупатель — публичный каталог (`/buildings?organization=…`), бренд
  (`/public/brand`), AI-помощник гостя (`EstateContext`) и `/public/green-impact`: скрытого дома там нет. Покупатель
  со сделкой в скрытом доме видит в кабинете свою квартиру, график, платежи, документы и чат, как раньше. AI в кабинете
  получает в контексте ЖК и дома его сделок, даже скрытые. Сотрудники видят дом в CRM с пометкой «скрыт с сайта»;
  статистика CRM считает все дома. На проде «Зелёный эффект» сайта уменьшится: демо-сделки — в скрытом доме.
- **Development** скрывать прежний дом не нужно: сидер разработки создаёт блоки рядом с ним, а на нём — тесты и
  демо-сделки. Сайт ЖК с блоками сам показывает только блоки (этап 3).
- **3D всего ЖК (этап 3).** Сцена строится из данных API: Footprint, SitePosition и Setbacks всех блоков, SitePlan
  организации. Модель — та же сцена (modeli-3d-bino-script.js). Блок — выдавленный контур по участкам этажей с
  одинаковым контуром: подиум 1–2 этажей облицован гранитом и выше (4,5 м), уступ последнего этажа — со своей террасой,
  стеклянным ограждением и тёплыми огнями ночью. Кромки плит каждого этажа, корона и парапет собраны в одну геометрию
  на блок. Окна раскладываются по фасаду каждой квартиры, по той же раскладке этажа, что и 2D-план
  (S.geom.floor): окно принадлежит своей квартире своего блока, а у квартиры несколько окон. Окна всех блоков — один
  InstancedMesh, поэтому весь ЖК рисуется примерно в 100 draw calls (было 239 у одного дома). У каждого блока свой
  оттенок облицовки.
  Без контура — один прямоугольный дом прежнего размера (тот же путь кода).
- **Двор, паркинг, лифты в 3D.** Зоны двора — из SitePlan, и рисуются, только если удобство есть в Amenities блоков:
  мини-футбольное поле (газон с разметкой, ворота, сетка) и детская площадка (мягкое покрытие, горка, качели,
  песочница). Режим «Паркинг»: блоки полупрозрачные, земля и двор убраны, видны уровни −1/−2 с местами в цветах
  статусов (клик — машино-место). «Разрез: лифты»: в ядре каждого блока по 3 шахты от −2 до крыши, кабины ездят
  (на низшем качестве — без анимации).
- **Размерная линия «≈ 26 м · по концепту»** — между соседними по порядку блоками, ближайшие точки контуров
  (S.geom.closest), только на виде «Сверху».
- **FPS и draw calls (Chrome на этой машине).** До — один дом 20 × 4 (мок): 1440 × 900 — около 34 FPS, 239 draw calls;
  375 × 812 — около 60 FPS, 195. После — весь ЖК со стенда (3 блока, около 2 400 окон, паркинг, двор): 1440 × 900 —
  около 35 FPS, 105 draw calls (авто-качество 1); 375 × 812 — около 61 FPS, 93. Бюджеты «телефон ≥ 45» и
  «draw calls ≤ 300» выполнены. 40 FPS на десктопе 1440 × 900 эта машина не даёт и в старой сцене: упор в заливку
  пикселей. На слабом GPU авто-снижение качества выключает тени.
- **Нумерация в блоках ЖК.** Квартиры каждого блока — 1…N подряд: с 3-го этажа снизу вверх, на этаже по часовой
  стрелке (на плане) от квартиры у лифтового холла — ближайшей к ядру с лифтами позиции раскладки (S.geom.floor;
  в сидере — StartSlot, на этаже пентхаусов — TopStartSlot; e2e numbering.spec.js сверяет их с геометрией этажа).
  Пентхаусы продолжают нумерацию (у A — кв. 153–156). Магазины — своя серия Н-1, Н-2… (1-й этаж, затем 2-й),
  машино-места — М-1… **по паркингу своего блока** (−1, затем −2): паркинг строится под каждым блоком, место
  покупают вместе с квартирой этого блока, и номер «A-М-12» сразу говорит, к какому подъезду идти; общая нумерация
  по всему паркингу ЖК дала бы трёхзначные номера без указания блока.
- **Номер для людей** — «Блок A, кв. 45», кратко «A-45», магазин — «Блок A, пом. Н-3» («A-Н-3»), машино-место —
  «Блок A, м/м М-12» («A-М-12»). Код Н-/М- один на всех языках, как табличка на двери. В базе номер — число,
  серия — вид помещения (Kind); API отдаёт blockCode и вид (apartmentKind) рядом с номером, текст собирают
  UnitNames (C#: PDF, письма, Telegram, AI, журнал) и S.unitName/S.aptNum (сайт, кабинет, CRM). Во фразах писем и
  Telegram — «кв. 45 в блоке A». Прежний дом без блока («Некруз Резиденс») не перенумерован и выглядит как раньше: «кв. №1201».
- **Уникальность номера в пределах дома (блока)** — в базе: Apartments.BuildingId (дом этажа; заполняет триггер
  `trg_apartments_building` — и для вставок EF, и для seed.sql) и три частичных уникальных индекса
  (BuildingId, Number): квартиры и пентхаусы, магазины, машино-места. Повтор — 409 `apartment_number_taken`.
  Миграция ApartmentBlockNumbering ничего не перенумеровывает: если в каком-то доме номера уже повторяются, она
  останавливается с текстом, где именно (номера правят в CRM и запускают миграцию снова). Проверка до миграции на
  проде — запрос в отчёте PR.
- **«3D на весь экран» — раскладка.** Сверху слева «← Каталог», кикер с именем ЖК и заголовок выбранного («Весь ЖК»,

  сворачиваемая панель 340 px: на «Весь ЖК» свёрнута (язычок «Квартиры · N»), при выборе блока открывается; один дом
