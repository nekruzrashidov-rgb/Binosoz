# Принятые решения

- Решение в формате `Sitora.sln` (шаблон .NET 10 по умолчанию создаёт `.slnx`, но в ТЗ указан `.sln`).
- Domain подключает только `Microsoft.Extensions.Identity.Stores`, чтобы `AppUser` наследовал `IdentityUser<Guid>`; EF Core и HTTP в Domain нет.
- Роли хранятся в таблицах Identity (`Roles`, `UserRoles`), а не отдельным полем `Role` в `Users`; таблицы Identity переименованы без префикса `AspNet`.
- Добавлено пятое исключение домена `UnauthorizedException` (→ 401) для неверного входа и истёкшей сессии.
- Refresh-токен: 64 случайных байта, в базе только SHA-256 хеш, срок 30 дней, ротация при каждом обновлении; повторное использование старого токена отзывает все сессии пользователя.
- `POST /auth/logout` принимает refresh-токен в теле и не требует access-токена; повторный выход отвечает 204.
- Добавлен `GET /api/v1/auth/me` для проверки токена и получения текущего пользователя.
- Вход блокируется на 15 минут после 5 неудачных попыток (lockout Identity).
- В JWT роли лежат в claim `role`, идентификатор пользователя в `sub` (`MapInboundClaims = false`).
- Миграции в Development и Staging применяются при старте; в Production — только командой `--migrate` (изменено при доработках по новому ТЗ, см. ниже). Роли создаются всегда, пользователи сидера только в Development.
- Если переменная с паролем пользователя сидера не задана, пользователь не создаётся, в лог пишется предупреждение.
- Swagger включён во всех окружениях, кроме Production.
- `Microsoft.EntityFrameworkCore.Design` и фабрика контекста для `dotnet ef` лежат в Infrastructure; `dotnet-ef` установлен локальным инструментом (`dotnet-tools.json`).
- PostgreSQL из docker-compose проброшен на порт 5433, чтобы не конфликтовать с локальным сервером на 5432.
- Тесты используют Testcontainers (`postgres:18`); если Docker недоступен, можно задать `SITORA_TEST_DB` со строкой подключения к своему серверу — тесты создадут и удалят временную базу.

## Этап 2. Каталог и заявки

- `Building.FloorsCount` — число жилых этажей; коммерческий этаж 0 существует отдельно, номер этажа допустим от 0 до `FloorsCount`.
- Каталог отдаёт этаж 0 вместе с жилыми (флаг `isCommercial`), поэтому у «Sitora Residence» 17 этажей: 16 жилых по 8 квартир (128) и коммерческий без квартир.
- Номер квартиры — целое число; в сидере это `этаж × 100 + позиция` (101…1608). Уникальность — `(FloorId, Number)`, как в ТЗ.
- Студия хранится как `Rooms = 0`.
- Цена квартиры везде округляется до 100 сомони (не только в сидере), чтобы правило было одно; валюта каталога — TJS.
- Статус квартиры — `private set` в сущности, менять его можно только методами `Book`, `ReleaseBooking`, `Sell`, `SetOnRequest`.
- «Под запрос» включается и выключается отдельным `PATCH /apartments/{id}/on-request` (Content, Admin), только из статуса Free и обратно; через PUT статус не меняется.
- Сидер ставит квартирам только Sold, Free и изредка OnRequest; статус Booked без записи брони был бы несогласованным, поэтому брони появятся в сидере на этапе 3.
- Перечисления хранятся в базе строками (нужно для частичного индекса брони по `Status = 'Active'`).
- Пагинация: `page` от 1, `pageSize` по умолчанию 20, максимум 100; неверные значения приводятся к допустимым без ошибки.
- Кэш каталога — `IMemoryCache` на 30 секунд; любое изменение каталога или статуса сбрасывает весь кэш каталога сразу. Кэш живёт в памяти процесса, при нескольких экземплярах API понадобится Redis.
- Язык названия дома выбирается по `Accept-Language` (`tg` → `NameTg`, иначе `NameRu`); в ответе также есть оба варианта для CRM.
- Импорт Excel: первый лист, строка заголовков, столбцы этаж, номер, комнат, площадь, цена за м². Недостающие этажи создаются, существующие квартиры обновляются, статусы не импортируются. При любой ошибке ничего не сохраняется, ответ 422 со списком ошибок по строкам. Лимит файла 5 МБ.
- Аудит (`IAuditService`) сделан уже на этапе 2, чтобы писать изменения цен; запись сохраняется в той же транзакции, что и изменение. Просмотр аудита — этап 3/Admin.
- `Notification.UserId` может быть пустым: так записываются сообщения в общий канал менеджеров.
- Telegram-заглушка пишет сообщение в лог Serilog и в таблицу `Notifications`. Сбой отправки не отменяет заявку: заявка сохраняется раньше уведомления.
- Телефон нормализуется к `+992XXXXXXXXX`; принимаются 9 цифр или 12 с кодом 992. Номера других стран пока не принимаются.

## Этап 3. Бронь и CRM

- Admin входит во все наборы ролей: эндпоинты «для Manager» доступны и Admin.
- Двойная бронь исключается дважды: строка квартиры блокируется `SELECT … FOR UPDATE` в транзакции, и частичный уникальный индекс `IX_Bookings_ApartmentId_Active` не даёт записать вторую активную бронь. Оба случая отвечают 409.
- Те же блокировки берут продление, отмена, снятие брони задачей и операции сделки, чтобы они не пересекались.
- Гостевая бронь создаёт заявку (или берёт открытую заявку с тем же телефоном). Гость не может держать больше одной активной брони на номер; менеджер — без ограничения.
- Бронировать на существующего клиента (`customerId`) может только Manager/Admin, гость получает 403.
- Продление добавляет 48 часов к более позднему из «окончание брони» и «сейчас». Отмена требует причину.
- Hangfire использует то же хранилище PostgreSQL (схема `hangfire`). Дашборд Hangfire не включён: у него своя авторизация через cookie, а в API только JWT.
- Сервер Hangfire выключается переменной `Hangfire__ServerEnabled=false` (так делают тесты и можно делать на лишних экземплярах API).
- Добавлен этап сделки `Cancelled` («Отменена»): без него брошенная сделка навсегда занимала бы квартиру. `Completed` и `Cancelled` — конечные, этап после них не меняется.
- На квартиру допускается одна неотменённая сделка (частичный уникальный индекс `IX_Deals_ApartmentId_Open`).
- Сделка держит квартиру с этапа «Бронь» (Booked) и продаёт с «Договора» (Sold). При возврате назад квартира возвращается в Booked или Free; для этого добавлен переход Sold → Booked (`RevertSale`).
- Если на квартире активная бронь этого же покупателя (по клиенту или по телефону заявки), сделка забирает её: бронь становится Converted, сделка начинается не раньше «Брони», заявка закрывается. Бронь другого человека — 409.
- Сделки пока только в TJS; USD отклоняется (422) до этапа 4, где появится курс НБТ.
- Скидка: от 0 и меньше цены, при скидке больше нуля нужна причина. Меняется только при создании сделки.
- Менеджеры видят все сделки и заявки (одна команда продаж), не только свои.
- Клиента можно завести из заявки (`leadId`): заявка становится Converted, её активные брони переходят на клиента.
- Паспортные данные шифруются AES-256-GCM ключом `Encryption__Key` (32 байта, base64) и отдаются только в карточке клиента (`GET /customers/{id}`), не в списке и не в аудите.
- `/crm/pipeline`: колонки по этапам от «Заявки» до «Завершена». В «Заявке» также открытые заявки без активной брони, в «Брони» — активные брони без сделки. До 50 карточек на колонку, `count` — полное число.
- `GET /audit` (Admin): фильтры `entity`, `entityId`, `from`, `to`, сортировка от новых к старым.
- Сидер: 10 клиентов, 5 сделок на этапах Lead…Payment на свободных квартирах верхних этажей, 2 брони с сайта на 48 часов. Пароли и паспорта выдуманные.
- `Newtonsoft.Json` закреплён на актуальной версии: Hangfire по умолчанию тянет 11.0.1 с известной уязвимостью.
- Пользователи (`GET`/`POST /users`) в ТЗ не привязаны к этапу; сделаны на этапе 4 вместе с учётными записями покупателей.

## Этап 4. Кабинет покупателя

- Вход по SMS только для тех, кто уже есть в клиентах (по телефону). Ответ `sms/send` одинаковый для любого номера (202), чтобы по нему нельзя было узнать, кто покупатель; SMS уходит только клиентам.
- Код: 6 цифр, живёт 5 минут, 5 попыток ввода; в базе хранится SHA-256 от «телефон:код». Не больше 5 кодов в час на номер, дальше 429.
- При первом входе создаётся пользователь с ролью Customer (логин — телефон, без пароля) и привязывается к клиенту.
- `RequireUniqueEmail` в Identity выключен (у покупателей нет почты); уникальность почты держит частичный уникальный индекс `EmailIndex`.
- Ошибки Identity (пароль и т. п.) переведены на русский (`RussianIdentityErrorDescriber`).
- `POST /users` создаёт только сотрудников (Admin, Manager, Accountant, Content); пароль задаёт администратор.
- Покупатель получает список своих сделок через `GET /me/deals`; график, документы и акт сверки — по общим адресам `/deals/{id}/...`. Для чужой и несуществующей сделки ответ одинаковый — 404. Content к сделкам доступа не имеет (403).
- «Сотрудник» в правах на график, документы и акт сверки — это Manager, Accountant и Admin.
- График: день платежа 1–28 (чтобы он был в каждом месяце), срок 1–360 месяцев, взнос от 0 до 100% не включая 100. Взнос — в дату начала, месячные платежи — с месяца после неё. Взнос и месячный платёж округляются до целой единицы валюты договора (сомони или доллар), остаток округлений — в последнем платеже.
- Пересоставить график можно, только пока по сделке нет платежей. Составляет график Manager (как в ТЗ) и Admin.
- Распределение оплат не хранится отдельно от платежей: после каждого платежа или сторно все пункты графика пересчитываются от общей оплаченной суммы, начиная с самых ранних.
- Платёж без графика не принимается (422); сумма сверх остатка по договору — тоже; дата оплаты — календарная дата по Душанбе, не в будущем.
- Сделки в USD включены: цена = цена квартиры в сомони ÷ курс на сегодня, округление до 1 доллара; без курса — 422.
- Пересчёт платежа: берётся курс USD на дату оплаты или ближайший более ранний (НБТ не публикует курс в выходные). `RateUsed` хранится, если хоть одна из валют — USD; для сомони к сомони он пустой. Сохраняются сумма в валюте платежа, в валюте договора и в сомони.
- Сторно копирует суммы и курс исходного платежа с обратным знаком, датой ставится день исправления. Сторнировать можно один раз (уникальный индекс по `ReversalOfId`), сторно сторнировать нельзя.
- Платежи и сторно по одной сделке идут по очереди (блокировка строки сделки `FOR UPDATE`).
- Курс: ручной ввод `PUT /rates` (Accountant, Admin) на дату не дальше завтрашней; повторный ввод на ту же дату перезаписывает. Курс хранится с 4 знаками. `GET /rates/current` открыт всем.
- Задача `update-rates` (каждый день 05:00 UTC = 10:00 Душанбе) вызывает `IRateProvider`; сейчас это заглушка, которая ничего не загружает и пишет предупреждение. Загруженный курс не перезаписывает введённый вручную.
- Курс USD в сидер не добавлен, чтобы не выдумывать банковские данные; сделки сидера — в сомони.
- Документы: PDF, PNG, JPG, DOCX до 20 МБ, тип проверяется по первым байтам файла. Загружают Manager, Accountant, Admin; смотрят и скачивают владелец сделки и они же. Файлы лежат в `Storage:RootPath` (в Docker — том `files`), ключ формирует сервер.
- Акт сверки: на дату `?date=YYYY-MM-DD` (по умолчанию сегодня по Душанбе). Начислено — сумма пунктов графика со сроком до этой даты, оплачено — платежи и сторно до этой даты в валюте договора, задолженность — начислено минус оплачено (не меньше нуля), остаток — сумма договора минус оплачено.
- PDF строится QuestPDF под Community-лицензией (бесплатна для компаний с годовой выручкой до 1 млн долларов — перед продакшеном проверить, подходит ли застройщику). Шрифт — встроенный в QuestPDF Lato: в нём есть кириллица и таджикские буквы, системные шрифты не нужны.
- О новом платеже и документе покупателю отправляется уведомление через `INotificationSender` (сейчас та же Telegram-заглушка), если у клиента уже есть учётная запись.
- SMS-заглушка пишет в лог текст вместе с кодом — это нужно для разработки. Перед продакшеном её нужно заменить настоящим провайдером.

## Этап 5. Стройка и чат

- У этапа стройки есть порядок (`SortOrder`) и процент 0–100 (ещё и проверка в базе). Общая готовность дома — среднее процентов этапов, округлённое до целого.
- Добавлен `POST /buildings/{id}/stages` (Content, Admin): в ТЗ есть только PUT, а этапы нужно как-то создавать.
- Ход стройки видят сотрудники (Manager, Accountant, Content, Admin) и покупатели, у которых есть неотменённая сделка в этом доме; остальным покупателям — 404. Гостям не виден (в ТЗ — «покупатель, Content»).
- Фото: PNG или JPG до 10 МБ, тип проверяется по первым байтам (общая проверка с документами — `FileTypes`). Отдаются через `GET /construction/photos/{id}` с той же проверкой доступа; в ответе этапа — готовый адрес фото.
- Чат: по одной ветке на сделку, писать могут владелец сделки и Manager, Accountant, Admin. У сообщения хранится сторона (`FromCustomer`); при чтении истории сообщения другой стороны отмечаются прочитанными (`ReadAt`).
- История — от новых к старым, постранично. Длина сообщения 1–2000 символов.
- SignalR-хаб `/hubs/chat`: `JoinDeal(dealId)` с проверкой доступа (чужая сделка — ошибка «Сделка не найдена»), `SendMessage(dealId, text)`, событие `messageReceived`. Сообщения, отправленные через REST, тоже рассылаются в хаб.
- Токен для хаба можно передать в `access_token` строки запроса (браузер не ставит заголовок для WebSocket); это принимается только для путей `/hubs`. Serilog пишет в лог путь запроса без строки запроса, токен туда не попадает.
- Пользователь в вызовах хаба берётся из `Context.User` (класс `HubCaller`), а не из `HttpContext`.
- О новом сообщении второй стороне уходит уведомление: от покупателя — в общий канал менеджеров, от сотрудника — покупателю лично.
- SignalR пока работает внутри одного экземпляра API. Для нескольких экземпляров понадобится backplane (Redis).
- Сидер: 8 этапов стройки «Sitora Residence» с примерными процентами, без фото.

## Этап 6. Запуск

- Лимиты запросов — встроенный `RateLimiter` ASP.NET Core, фиксированное окно на IP: вход и refresh — 10 в минуту, `sms/send` и `sms/verify` — 20 в час, заявки и гостевые брони — 30 в час (сотрудники с токеном не ограничены). Значения — в `RateLimiting:*`. Лимит 5 кодов в час на номер остаётся в сервисе.
- Лимиты хранятся в памяти процесса; при нескольких экземплярах API их нужно переносить в Redis.
- HTTPS завершает Caddy (`docker-compose.prod.yml`, `deploy/Caddyfile`): он сам получает сертификат и редиректит HTTP. Приложение в Production добавляет HSTS на 1 год и `UseHttpsRedirection` на случай обращения в обход прокси.
- `X-Forwarded-For/Proto` принимаются только при `ForwardedHeaders__Enabled=true` и от одного прокси; в prod-compose API не открыт наружу. Без этого IP для лимитов был бы IP Caddy.
- CORS: `Cors:AllowedOrigins`, с `AllowCredentials` (его требует клиент SignalR в браузере). В Development разрешены `localhost:3000` и `localhost:5173`.
- Защитные заголовки — свой небольшой middleware; заголовок `Server` убран в Kestrel.
- Первый администратор вне Development создаётся из `BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD`, только если админов ещё нет.
- Добавлен `PATCH /users/{id}/status` — блокировка сотрудника с отзывом его refresh-токенов (нужно, чтобы уволенный сотрудник терял доступ).
- SMS-заглушка вне Development не пишет код в лог, только маскированный номер.
- Логи в Production — JSON в stdout (компактный формат Serilog), их собирает docker.
- Бэкап: `pg_dump --format=custom` из контейнера базы и tar папки файлов из контейнера API, хранение 14 дней, временные файлы, чтобы недописанный бэкап не выглядел готовым. Восстановление — `pg_restore --clean` с остановкой API и подтверждением.
- `.gitattributes` закрепляет LF для `.sh`, `Caddyfile`, `*.yml` и `Dockerfile`: с CRLF они не работают на Linux.
- Образ Caddy — `caddy:2` (последний второй мажор); PostgreSQL — `postgres:18`, как в ТЗ.
- Деплой и Docker не проверены на чистой машине: на машине разработки нет WSL, VPS нет. Это записано в README как известное ограничение.

## Доработки по новому ТЗ (D:\Downloads\TZ.md)

- Миграции — отдельной командой при деплое: `dotnet Sitora.WebApi.dll --migrate` применяет миграции, создаёт роли, первого админа (и в Development — данные сидера) и выходит, не поднимая сервер. В Production API сам миграции не применяет (`Database:MigrateOnStartup` по умолчанию `false`) и при неприменённых миграциях не стартует с подсказкой команды. В prod-compose команду выполняет сервис `migrate`, API ждёт его успешного завершения.
- График показывает эквивалент во второй валюте (TJS ↔ USD) по текущему курсу — последнему не позже сегодняшнего дня — с пометкой «оценочно» (`Equivalent` в ответе и `AmountDueEquivalent`/`AmountPaidEquivalent` у пунктов). Без курса эквивалента нет (`null`). Суммы к оплате и распределение платежей не меняются: платёж по-прежнему пересчитывается по курсу на дату оплаты.
- PDF графика платежей: `GET /deals/{id}/schedule.pdf`, права как у графика. Данные те же, что в `GET /deals/{id}/schedule` на сегодня: пункты со статусами, итоги и, если введён курс, колонка оценочного эквивалента со сноской. Шапка сделки общая с актом сверки.
